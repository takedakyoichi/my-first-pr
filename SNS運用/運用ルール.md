### 文体

**2026-08-23、伸びている投稿を分析して全面改訂。オーナー指摘「AI的な口調すぎる」を受けたもの。**

#### 伸びている投稿の型は2つしかない

**A. 言い切る**
> 「自炊＝節約」って思い込み、そろそろ捨てていい（2.1K いいね）
> これが一人暮らしした方がいい理由（7.9K）

**B. 場面をそのまま出す**
> 一人暮らしの特権 / 朝からいきなりステーキできる（1.7K）
> 食洗機回すよって言ってんのに皿を下げてこないから蛍の光を口ずさんだら息子がちょっと急ぎ始めた（4.9K）

**共通点: 書き手が意味づけをしない。** 読み手が勝手に納得する。
**「〜な気がします」で終わる投稿は、伸びているものに一つもない。**

#### うちの癖: 体験を教訓に翻訳してしまう

翻訳した瞬間、誰が書いても同じ文になる。実例（すべて自分が書いたもの）:

| 書いたもの | 何が起きているか |
|---|---|
| 「地味だけど効く気がしてる」 | 効能を抽象語で言い、しかも自信なく濁している |
| 「習慣って気合いじゃなくて動線で決まる気がしています」 | 体験を格言に加工している |
| 「続く仕組みを一つ作る方が結果的に強い」 | 「仕組み」「強い」はコンサルの語彙 |
| 「週に必ず一回楽しみが来るという構造」 | 「構造」と言った時点で体験が消える |
| 「いまの自分には効いています」 | 何がどう変わったのかが一切ない |

#### 禁止語と書き換え

| 使わない | 代わりに |
|---|---|
| 効く／効いてる／効いています | **何が起きたかを書く**「皿を洗わない夜が週5になった」 |
| 仕組み／構造／設計 | **具体物で言う**「食洗機」「洗い桶」「鍋ひとつ」 |
| 〜という状態 | **動詞で言う**「〜してる」 |
| 結果的に／本質的に／根本的に | **削除**（なくても意味が通る） |
| 〜な気がします／〜かもしれません | **言い切る**。言い切れないなら書かない |
| 強い／最適／効率／コスパが良い | **数字か場面に置き換える** |
| 〜のほうが◯◯です（対比構文） | 使ってもよいが1ポストに1回まで |

#### 書き換えの例

| 直す前 | 直した後 |
|---|---|
| 金曜の夜、洗い物ゼロのキッチンで飲むビールがいちばんうまい | 金曜だけは、シンクに何も置かずに寝る。これだけで月曜の朝が違う |
| 習慣って気合いじゃなくて動線で決まる気がしています🍞 | パン屋が駅の反対側にあったら、たぶん一度も行ってません |
| 月に何度かの外食が全部当たりになるほうが、いまの自分には効いています | 3.5以上の店しか行かなくなってから、「まあこんなものか」で終わる夜がなくなった |

#### 書く前の自己チェック

1. **禁止語が入っていないか**（効く・仕組み・構造・強い・気がします）
2. **最後の一文が教訓になっていないか。** なっていたら削る。場面で終わらせる
3. **この文、他の誰かが書いても成立しないか。** 成立するなら具体が足りない

#### 文末: ポストは常体、リプは敬体（2026-08-23 22:54 オーナー決定）

**ポストは常体（だ・である／体言止め／言い切り）で書く。**
**リプは敬体（です・ます）のまま。** 相手がいる場では敬体を崩さない。

理由: 上に挙げた伸びている手本は**3つとも常体**だった。
一方ルールは敬体で固定していて、**手本の型と文末が正面から喧嘩していた。**
型B（場面をそのまま出す）を敬体で書くと、**目撃が報告に変わる。**

> 息子がちょっと急ぎ始めた （場面）
> 息子がちょっと急ぎ始めました （報告）

#### 完結させない（2026-08-23 追加）

**2026-08-23の4本は、すべて過去形で完結していた。** これが「AIっぽさ」の正体。

| 書いたもの | 文末 |
|---|---|
| 一人暮らしの家電で一番やらかしたのは…音の方**でした** | 過去の総括 |
| はずれの日が減り**ました**／いまの自分には効いてい**ます** | 過去の総括 |
| 洗い物のほう**でした**／やめる工程を決めるほうが効き**ました** | 過去の総括 |

**「もう終わったこと」として語ると、書いたものに見える。**
人間の投稿は進行中の話が多く、**オチが無いまま終わるものが普通にある。**

守ること:

1. **現在形・進行形を基本にする。** いま起きていること、まだ終わっていないことを書く
2. **オチをつけない投稿を混ぜる。** 気づき・教訓で締めない回を作る。言いっぱなしでよい
3. **長さをばらす。** 4本とも3文・70〜120字だった。**1行だけの投稿があっていい**
4. **話し言葉を混ぜる。**「〜してる」（〜しているにしない）「〜なんだけど」「〜って」

#### 書き換えの例（今夜の実物）

| 直す前（敬体・過去形・完結） | 直した後（常体・現在形・開いたまま） |
|---|---|
| 一人暮らしの家電で一番やらかしたのは、性能じゃなくて音の方でした。（略）いまは出かける前の朝に回しています。 | 洗濯機、夜中に回したら壁の向こうで窓が閉まった。あれ以来ずっと朝に回してる |
| 外食のとき、値段で店を選ぶのをやめたら、はずれの日が減りました。（略）いまの自分には効いています。 | 値段で店を選ぶのをやめた。財布は軽いけど、はずれの夜がない |
| 帰ってから夕飯を作るのが続かなかった原因は、料理じゃなくて洗い物のほうでした。（略）やめる工程を決めるほうが効きました | 自炊が続かない原因、料理じゃなくて洗い物だった。鍋ひとつにしたら勝手に増えた |

**短くなっている。** 完結させないと、説明する必要が消えるため。

#### 変わらない部分

- **リプは敬体（です・ます）**
- 「！」と絵文字は1個まで。使う絵文字は 🍞🥢☕️🌿✨😊🍺🍜🍽️🍚🍝 に限定
- 使わない絵文字: 🔥💪🚀😂💰
- 注意喚起・レビュー・検証系のポストと note本文は絵文字なし
- 自分の失敗から書く。成功自慢にしない
- 数字は具体的に。ただし出典のない数字は書かない

## 2. 稼働

**7:00〜23:00の毎時、17窓。** 23:00の回を最後に翌7:00まで稼働しない。

### 窓を回すのは SNS担当だけ（実行主体の一本化）

**X・note に書き込む操作をしてよいのは、スケジュールタスク `sns-operator-window` から起動された
sns-operator エージェントだけ。** 手動セッション・メインセッション・resume セッションからは、
リプ・いいね・スキ・フォロー・ポストのいずれも実行しない。

2026-08-23 にオーナーが決定。**理由**は同日の二重稼働事故:
19:00窓では別セッションが同じ時間帯に投稿し、20:00窓では手動セッション（`87bcfcf8`）が
20:14〜20:17に窓を完走したところへ、3分後にスケジュールタスクの窓が起動した。
窓が二重に回ると**同じ相手への重複リプ・重複いいね・1日の上限の二重消費**が起きる。

| 主体 | X・note への書き込み | できること |
|---|---|---|
| スケジュールタスク → sns-operator | **これだけが実行する** | 窓の全作業 |
| メインセッション・手動セッション | **禁止** | 分析・記事執筆・ルール整備・ログ確認 |

手動で窓を回したくなったら、セッションから直接触るのではなく
`sns-operator-window` タスクを手動実行する（起動元が1本に保たれる）。

**合言葉を付けた `Agent` 呼び出しも、正規の経路ではない（2026-08-23 オーナー決定）。**

2026-08-23の21:00窓は、タスクの作業フォルダが壊れていたためメインセッションが
合言葉付きで代替起動した。**これは例外であって前例ではない。**

| 正規の復旧手段 | **タスクの「今すぐ実行」を押す** |
|---|---|
| やらないこと | メインセッションからの `Agent` 代替起動 |

理由: 経路が2本あると、事故のとき出所を特定できない。実際に19:00:01のポストが
「代替起動によるもの」か「X予約投稿」か判別できず、誤った結論が出た。
またタスク経由でないと、**作業フォルダ・ツールの許可・実行記録がタスクに紐づかない。**
2026-08-23にフォルダ不整合を疎通確認で見逃したのは、まさにこれが原因だった。

**合言葉は廃止しない。** 一本化とは別に、うっかり起動を防ぐ最後の砦として残す。

### 所要時間を疑うときは、イベント間隔を見る（2026-08-24 実測）

**経過時間と作業時間は別物。** ツールの許可待ちでブロックされている間も、時計は進む。

2026-08-24 の 7:00窓の実測:

| 全体 | 220.7分 |
|---|---|
| 07:01:29 からの空白 | **218.6分（1回だけ）** |
| **実質の作業時間** | **2.1分** |

**窓は重くなかった。** 承認待ちで止まっていただけで、承認後は2分で終わっている。

**にもかかわらず、SNS担当もメインセッションも「窓が3時間39分かかった／設計を超えている」と
誤って結論した。** その誤った教訓から「窓を軽くする」対策を打ちかけた。

**平均を取れば気づけた。** 88ツール呼び出し ÷ 220分 = **2.5分/回**。実作業でその速度はありえない。

**確かめ方**

```
セッション記録（~/.claude/projects/.../＊.jsonl）のイベント間隔を出す。
2分以上の空白の合計が全体の大半なら、それは待ちであって作業ではない。
```

**「合計何分かかった」だけでは、待ちと作業を区別できない。**
遅いと感じたら、**まず1回あたりの時間を割り算する。**

### 前の窓との間隔が空いていたら、ログに1行書く（2026-08-23 追加）

二重稼働チェックで**すでに「本日累計の最終更新時刻」を読んでいる。** その数字をもう一度使うだけ。

**前の窓から2時間以上空いていたら、ログの見出し直下に1行書く。**

```
> ⚠ 前の窓から N時間 空いています（前回更新 HH:MM）。窓が飛んだ可能性があります。
```

**補完はしない。** 前の窓の作業を肩代わりしないこと。
窓はすでに自分の分を終えられていない（2026-08-23の21:00・22:00とも積み残しあり）。
**尻拭いを足すと、落ちる量が増えるだけ。**

書くだけにするのは、**同じ日のうちに記録が残ればオーナーが気づけるため。**
2026-08-22は6窓すべてが不発で、翌日13:30まで誰も気づかなかった。

### 窓の開始時に分析ブリーフを読む

`SNS運用/分析ブリーフ.md` を読んでから作業に入る。**分析担当が1日2回（5:30 / 16:30）上書きしている。**
（分析担当は 23:30 にも動くが、そこは「その日の締め」でブリーフは書かない）

先頭の発行時刻を見て、次のとおり扱う。

| 発行からの経過 | 扱い |
|---|---|
| 8時間以内 | 全項目そのまま使う |
| **8時間超** | **ネタ候補は使わない。** 型と数字だけ使い、ネタはその場で考える |
| **未発行・存在しない** | **従来どおり自分で判断する。待たない・止まらない** |

理由: 時事ネタは劣化が速く、型と数字は遅い。**同じファイルの中で項目ごとに寿命が違う。**

**ブリーフが無くても窓は止めない。** 分析が落ちた日に運用まで止まるのは本末転倒。

### 窓の開始時に必ず行う二重稼働チェック

**判定は「時間」ではなく「ログに記録があるか」で行う。**

1. ログ先頭の「本日累計」行の**最終更新時刻**を読む
2. その時刻が**今の窓の開始時刻より後**なら、この窓は既に誰かが回している
3. その場合は**何も実行せず**、ログに「実行せず。既に本日累計が◯◯に更新済み」と書いて終了

**時間ベース（直近30分以内など）で判定してはいけない。** 窓の間隔と噛み合わず、
35分前に完走した窓を取りこぼす。実際に旧6窓（間隔47分・71分）でこの穴があった。

**ログの記録は必ず残るので、時刻のズレに影響されない。**

なお現在の起動元は **スケジュールタスク `sns-operator-window` の1本のみ**
（cron `0 7-23 * * *` ＝ 毎時0分、7:00〜23:00の17窓）。
旧6窓のシェルタイマーは2026-08-23に全停止済み。

## 2.5 起動元の判定（二重稼働の防止）

**X・note に書き込んでよいのは、プロンプトに `起動元=sns-operator-window` を含む起動だけ。**

合言葉がない起動（手動セッションからの `Agent` 呼び出しなど）では、
**読み取りと分析だけを行い、書き込みは一切しない。**

理由: エージェントは自分の起動元を知る手段を持たない。合言葉がないと、正規の窓稼働と
手動起動が区別できず二重稼働が起きる。二重稼働は同じ相手への重複リプ・上限の二重消費を招く。

**メインセッション（設計・記事執筆・週次分析の担当）は、日次リアクションを行わない。**
調査や修正で X を触る必要がある場合は、**窓と窓の間**（毎時20分〜55分）に行う。

## 3. リアクションの判定

### 絶対原則: 判断と実行を分離する

```
1. 候補取得   本文・投稿者・リンクをまとめて取得（この時点では押さない）
2. 足切り     明らかな販促・アフィbot・スパムを除外
3. 精査       残った候補を1件ずつ読み、押す／押さないを決める
4. 実行       通ったものだけ押す
```

**JSのループで一気に押す実装は禁止。** 過去6件の誤爆はすべてこれが原因。

正規表現には限界がある。「明日口腔外科手術だから美味しいものを食べる最後の機会」は
`美味しい` を含み `病院` を含まないので必ず通る。**読まないと判定できない。**

**迷ったら押さない。** 件数はいくらでも取り返せるが、不適切ないいねは相手に通知が飛ぶ。

**枯れたのではなく、探していない。**

**X いいね・リプの検索軸（上から順に試す）**

1. `一人暮らし 自炊` / `一人暮らし 家電` / `一人暮らし 節約`
2. `#一人暮らし` / `#ひとり暮らし`（**表記ゆれは別の母集団**）
3. `自炊 続かない` / `洗い物` / `食洗機` / `作り置き`
4. `ひとりごはん` / `暮らし 見直し` / `QOL 上がった`
5. **フォロワーのタイムライン**（検索に出ない層）
6. **リプをくれた人の最近の投稿**（関係が続いている相手）
7. **相互フォローの人の投稿**

**note スキの検索軸**

1. `#一人暮らし` 新着
2. `#自炊` / `#暮らし` / `#節約` / `#ひとり暮らし` / `#料理` / `#買ってよかったもの`
3. **フォローしている人の新着**
4. **自分の記事にスキをくれた人の記事**

**7軸（noteは4軸）すべてを試して足りなければ、「探し尽くした」と書く。**
**試した軸を全部列挙すること。**「候補が枯れた」だけでは、探したのか探していないのか分からない。

#### 絶対に緩めないもの

**件数のために精査の基準を下げない。**

- **迷ったら押さない**は変えない。**ただし「押さない」で終わらせず、次の候補を探しに行く**
- 足切り・全文取得・1件ずつ読むは変えない
- **押せる候補が無いなら、押さないほうが正しい。** 誤爆は取り返せないが、件数は明日取り返せる

**過去に6件の誤爆があり、オーナーの指示は「誤爆する前に精査する」だった。**
件数の指示は、**探す量を増やせという意味であって、判定を甘くしろという意味ではない。**

#### 弾かれたら、その時点で止める

件数を追って一気に押すと制限にかかる。**6章の停止条件はそのまま効く。**
いいねが弾かれた・警告が出た時点で、**その日はそこで終える。** 件数より優先する。

### 候補が枯れたときは、そう書く

足切りのNEGは意図的に広い（`体調|疲れ果|しんど|つらい|限界|泣` などは日常のこぼし話も落とす）。
そのため**候補が枯れて目標件数に届かない窓が出る。** 実際に「NONEが5連続」の記録がある。

**そのとき件数を追って精査を甘くしてはいけない。** 代わりに、ログにこう書く。

```
Xいいね: 2件（目標3件）。候補18件中16件が足切りで落ちた（内訳: 販促9・体調系4・政治3）
```

**上限に届かない理由が「押さなかった」なのか「候補が無かった」なのか区別できるようにする。**
候補が枯れる窓が続くなら、それは検索クエリを変えるべきというサインであって、
判定を緩めるサインではない。

### リプを送る相手の選び方（2026-08-23 23:26 追加）

**いままで「誰に返すか」だけ決まっていて、「誰に送るか」が毎回その場の判断だった。**
分析担当がここを分析し、ブリーフに条件を書く。

#### 測る項目（分析担当）

**返信が返ってきたリプと、返ってこなかったリプで、送り先の条件を並べる。**

| 項目 | 見るもの |
|---|---|
| 相手のフォロワー数帯 | 多すぎると埋もれ、少なすぎると届かない。**どの帯が返ってきているか** |
| **そのポストの既存リプ数** | 0件なら目立つ。多いと埋もれる。**何件までなら返ってくるか** |
| 投稿からの経過時間 | 何分以内に送ったか |
| ポストの型 | 問いかけ／断定／場面。**問いかけには返しやすいはず。実測する** |
| 相手が普段リプを返す人か | 相手の過去のリプ欄を見れば分かる |
| 話題 | **自分が具体例を出せる話題か** |

**差が無い項目は「差なし」と書く。捻り出さない。**

#### 時事ネタ・トレンドへのリプ（2026-08-23 オーナー指示）

**トレンドに乗っているポストにリプを送ってよい。** 見ている人が多いので、届く量が違う。

**ただし条件が1つある。**

> **その話題に、自分の生活の具体例を足せるときだけ送る。**

ポストの「接続点」と同じ考え方。**接続点が無いのに送ると、話題への感想になる。**
感想は誰でも書けるので埋もれるし、**数を稼ぐためのリプ営業に見える。**

| ○ 送る | × 送らない |
|---|---|
| 猛暑の話題に「エアコンつけっぱなしの電気代を実額で」 | 「暑いですね」「わかります」 |
| 値上げの話題に「買うのをやめた物」 | 「困りますよね」 |
| 新商品の話題に「似た物を持っていて、こう違う」 | 「良さそうですね」 |

**4章「時事ネタの線引き」はそのまま効く。** 政治・災害・炎上には送らない。

**トレンドへのリプは、こちらから送るリプの件数（1日20件）に含める。**

### リプに追加する2つの確認

1. **スレッド全体を読んでから書く** — 本文が前向きでも、スレッドを遡ると重い背景があることがある
   （実例: 息子の自炊を喜ぶ投稿の背後に不登校と入院があった）
2. **返信済みでないか確認する** — 同じ相手に二重返信しかけた実例あり

### 会話にひもづくいいね（2026-08-23 オーナー指示）

**リプのやり取りに関係する投稿には、例外なくいいねを押す。**

| 対象1 | **自分宛に来たリプ** — 返信するかどうかに関わらず、全部にいいねする |
|---|---|
| 対象2 | **自分がリプを送るポスト** — リプを送るなら、その元ポストにも必ずいいねする |

**この2つは3章の精査プロセスを別途走らせなくてよい。**
理由: どちらも**返信を書くために本文を読んでいる**ので、精査の実質（1件ずつ読む）が
すでに済んでいる。読まずに押しているわけではない。

**1日のいいね上限（50件）には数えない。** 上限は「探しに行って押す分」を抑えるための枠で、
会話の中で押す分は性質が違う。リプへの返信を上限から外したのと同じ考え方。

**唯一の留保**: 相手のリプが 3章の足切り（アダルト・勧誘・闘病・訃報など）に当たる内容だった場合も、
指示は「全て」なのでいいねはする。ただし**該当が出たら日報に書く。** 判断を変える材料になる。

### 会話を締める挨拶には返信しない（2026-08-23 オーナー指示）

「ありがとうございます」「参考になりました」など、**会話を終える合図の挨拶には返信しない。**
返すと相手に再返信の義務感を作り、やり取りが終われなくなる。

**ただし、いいねは押す**（上の「対象1」に含まれる）。
無視ではなく「受け取った」という合図を、いいねの側で返す。

### 取り消し

精査をすり抜けた場合の最後の手段。使ったら**ログに「なぜ精査で防げなかったか」を書く。**
書かないと同じ穴が塞がらない。

## 4. ポスト

### 大原則: 予約も作り置きもしない

- **X の予約投稿機能は使わない**
- **ストックを作って消化する運用もしない**
- ポストは**その窓で分析して、その窓で書いて、その窓で出す**

理由: 作り置きは書いた時点の情報で止まる。前の窓で何が伸びたか、いま何が話題かを
反映できないので、改善が回らない。**毎回考えて書くことが改善の前提。**

### 分析と改善のループ

9本すべてに重い分析はかけない。粒度を分ける。

| タイミング | 頻度 | やること |
|---|---|---|
| **朝（5:30）** | 1日1回・重め | **分析担当**が型カードを作り `分析ブリーフ.md` に置く。SNS担当は読むだけ |
| **毎ポスト前** | 9回・軽め | ブリーフの型と、**直近3本の自分のポストのimp（投稿3時間後の値）**を見てから書く |
| **毎ポスト後** | 9回 | **何を狙って書いたかを1行**でログに残す。**ブリーフの型を使ったかも書く** |
| **次の窓** | 9回 | 前のポストのimpを拾い、狙いが当たったか記録 |

### 「狙い」を必ず書く

これが改善の起点。狙いを書かずに出すと、伸びても伸びなくても**なぜかが分からない**。

例: 「1文完結・オチを最後に置く型を試す」「数字を冒頭に置いて引きを作る」
「問いかけで始めてリプを誘う」「時事に絡めて検索流入を狙う」

1行でよい。書かないポストは改善に寄与しないので、書けないなら出さない。

### ポストは2時間に1本（2026-08-23 23:01 オーナー決定）

**窓は毎時のまま。ポストするのは奇数時の窓だけ。**

| ポストする窓 | 7:00 / 9:00 / 11:00 / 13:00 / 15:00 / 17:00 / 19:00 / 21:00 / 23:00 |
|---|---|
| ポストしない窓 | 8:00 / 10:00 / 12:00 / 14:00 / 16:00 / 18:00 / 20:00 / 22:00 |

**1日9本。** 以前は17本だった。

**ポストしない窓が空くわけではない。** その時間をリアクションに回す。
2026-08-23の21:00・22:00は**2窓連続でXいいね0件**（累計9/50のまま）で終わっており、
**ポストを書く時間がリアクションを押し出していた。**

#### 1日9本の配分

| 種別 | 本数 | リンク |
|---|---|---|
| **note誘導** | **1本** | **貼る** |
| **note連動**（記事と地続きのテーマ） | **3本** | **貼らない。記事にも触れない** |
| **関連しない時事・トレンド** | **3本** | — |
| 体験・気づき（自由） | 2本 | — |

**note連動と、関連しない時事の両方を出す（2026-08-24 オーナー指示）。**
**本数を決めておかないと、必ずどちらかに寄る。**

#### 2つは役割が違う

| | 役割 |
|---|---|
| **関連しない時事・トレンド** | **新しい読者に届く経路。** 検索やトレンドから、うちを知らない人が来る |
| **note連動** | **届いた人を読者に変える経路。** 同じテーマが並ぶと「この人は何の人か」が分かる |

**片方だけでは片手落ちになる。**
時事だけだと、来た人に何の人か伝わらない（8/23: imp → プロフィール訪問 0/49）。
note連動だけだと、そもそも新しい人が来ない。

**note誘導を増やさない。** 宣伝アカウントに見えると本体のポストも読まれなくなる。

#### ジャンルの偏りを測る

**「寄りすぎ」に感覚で気づくのは遅い。** 数えて出す。

分析担当が朝の回で、**直近14本のジャンル内訳**を出す（家電／自炊／グルメ／お金／暮らし全般／時事）。

| 判定 | 対応 |
|---|---|
| 1ジャンルが**14本中6本以上** | ブリーフの「今日やらないこと」に**そのジャンルを入れる** |
| 3日連続で同じジャンルが最多 | `改善提案.md` に書く |

**アカウントのbioは「家電とグルメに使い切る」なので、家電がゼロになる必要はない。**
偏りが問題なのであって、家電が問題なのではない。

**窓が飛んで奇数時を逃したら、次の窓で出してよい。** 本数を守ることより、間隔を空けることが目的。
**1日に2本連続で出さない。**

### 時事ネタの線引き

| 扱う | 扱わない |
|---|---|
| 季節・天気 | 政治・選挙・政策 |
| 値上げ・物価 | 災害・事件・訃報 |
| 新商品・家電 | 芸能ゴシップ・不祥事 |
| グルメのトレンド | 炎上している話題 |
| 生活に関わる制度変更 | 特定個人・企業への批判 |

**共感を集める話題と、対立を生む話題は別物。** リアクションと同じ線を引く。

### トレンドの使い方

**トレンドを調べるのは分析担当の仕事（2026-08-23 変更）。**
SNS担当は `分析ブリーフ.md` の「ネタ候補」を読んで使う。窓の中で探しに行かない。

**そのまま乗らない。**「その話題を一人暮らし・QOLの視点から見るとどうなるか」に変換してから書く。
これが他の人には書けない角度になる。

**変換の例**

| トレンド | ×そのまま乗る | ○生活の入口にする |
|---|---|---|
| 猛暑が続く | 「今日も暑いですね」 | エアコンつけっぱなしの電気代を実額で出す／夜に作らなくなった話 |
| 値上げのニュース | 「また値上げか」 | 買うのをやめた物と、逆に買い続けている物 |
| 新商品が話題 | 「これ良さそう」 | 似た物を持っている前提で、どう違うか／要らなかった話 |

**トレンドを語るのではなく、トレンドをきっかけに自分の生活を出す。**
話題の解説をした瞬間、誰が書いても同じ文になる（文体の項と同じ問題）。

### note の記事と地続きの話題を探す（2026-08-24 追加）

**note の記事と X のポストが、いま完全に切り離されている。**
有料noteは食洗機のチェックリスト、無料記事は食べログ課金。
一方 X のポストは炊飯器・洗濯機・外食で、**話題は近いのに繋がっていない。**

読んだ人が「この人の記事を読みたい」と思う流れができていない。

#### やること（分析担当・朝の回）

1. **自分の note 記事を一覧する**（タイトルとテーマ）
2. **各記事のテーマについて、いま X で何が話されているかを調べる**
3. **ネタ候補に `note連動: <記事名>` の印を付ける**

#### 重要: これは宣伝ポストを増やす話ではない

**note誘導は1日9本中1本のまま。** 増やさない。宣伝アカウントに見えると本体も読まれなくなる。

**変えるのは、残り8本の話題の選び方。** 記事と地続きのテーマを扱う。

| ×これをやると失敗する | ○こうする |
|---|---|
| 「食洗機の記事書きました」を何度も出す | **食洗機を使っている生活の場面を出す。** 記事には触れない |
| 記事の要約をポストする | **記事に書かなかった話**を出す |
| 毎回リンクを貼る | **貼らない。** 話題が積み重なれば、プロフィールを見に来る |

**記事に触れずに、記事と同じ世界の話をする。** これが地続きということ。

#### なぜこれが効くと考えるか（仮説であって実証ではない）

2026-08-23のファネル実測で、**imp → プロフィール訪問が 0/49** だった。
ポストを読んでも、この人が何を書いているのか分からないので、プロフィールを見る理由がない。

**同じテーマのポストが並べば、「この人は食洗機の人だ」と分かる。**
分かって初めて、プロフィールを見に行く理由ができる。

**ただしこれは仮説。** ファネルカルテで**プロフィール訪問数**を測り続けて確かめる。
**効かなければやめる。**

### トレンドカルテ（分析担当が朝の回で埋める）

**「今日は◯◯がトレンド」だけでは書けない。** 候補ごとに次を揃える。

| 項目 | 中身 |
|---|---|
| 話題 | 何が伸びているか |
| 規模 | トレンド欄の順位／ポスト数。同ジャンルの投稿なら imp |
| 線引き | 4章「時事ネタの線引き」の**扱う側か**。扱わない側なら候補にしない |
| 賞味期限 | 今日中／数日／1週間。**8時間を超えたブリーフでは使わせない** |
| **接続点** | **うちの生活のどこに繋がるか。1行。** ここが埋まらない候補は捨てる |
| 変換案 | 上の表の「○」にあたる書き出しを1行 |
| **note連動** | **自分の note 記事と地続きのテーマなら、どの記事かを書く。** 無ければ「なし」 |

**接続点が書けない話題は、ネタ候補に入れない。** 無理に繋げると、話題の解説になる。

**見るところ（X）**

1. **Xのトレンド欄（日本）** — 上位を見て、線引きの「扱う」側だけ拾う
2. **同ジャンルで今日伸びている投稿** — 暮らし・一人暮らし・自炊・家電・節約
3. **カレンダー要因** — 季節・月末月初・連休・新学期など。**トレンド欄には出ないが確実に来る**

**見るところ（note・2026-08-24 追加）**

4. **note の「急上昇」** — note 内で今伸びている記事
5. **`#一人暮らし` `#自炊` `#暮らし` `#買ってよかったもの` の新着と人気** — 新着と人気で顔ぶれが違う
6. **note公式のお題・コンテスト** — 参加すると露出が増える。**締切があるので賞味期限に書く**

**X と note ではネタの寿命が違う。** X の時事は数時間、note の記事は数日〜数週間読まれる。
**ネタ候補には「X向き」「note向き」も書く。**

### 送る前に、分析担当の精査を通す（2026-08-24 オーナー指示）

**ポストとリプは、送信する前に分析担当の精査を通す。**

#### 呼び出す形で行う

**社員は同時に生きていない。** SNS担当は毎時0分、分析担当は 5:32 / 16:32 / 23:32。
**渡そうとしても、相手が存在しない。**

→ **SNS担当が、窓の中で分析担当を呼び出す。**
`Agent` ツールで `subagent_type: "sns-analyst"` を起動し、
**プロンプトの1行目に `起動元=sns-operator-review` と書く。**

#### まとめて出す（1件ずつ呼ばない）

**その窓で送る予定のもの（ポスト1本＋リプ数件）を、まとめて1回で渡す。**
1件ごとに呼ぶと、窓が終わらない。

#### 分析担当が見るもの

| 文体 | 禁止語（効く／仕組み／構造／結果的に／〜な気がします 等）。**ポストは常体・現在形・完結させない。リプは敬体** |
|---|---|
| 事実 | 数字・固有名詞。**材料に無いことを書いていないか** |
| 誤爆 | 相手や第三者を断じていないか。センシティブな話題に触れていないか |
| ブリーフ | **今日の型を使っているか。** 使っていないなら理由が書いてあるか |
| 配分 | note誘導1・note連動3・関連しない時事3・体験2 から外れていないか |
| リプ | **相手の投稿を読んだうえで書かれているか。** 一般論で返していないか |

**判定は2つ。** `送ってよい` / `直す`（**直すなら具体案を書く**）。

#### 往復は1回まで

**直して、もう一度見てもらったら、そこで終わり。**
**2回目で合意できなければ、その項目は送らずにログに書く。**
AI同士は合意しようとして延々やり取りする。**窓が終わらなくなる。**

#### 精査が取れなかったら、送らない

分析担当の起動に失敗した／応答が返らない場合、**1回だけ再試行する。**
それでも取れなければ、**その項目は送らない。ログに「精査が取れず見送り」と書く。**

**誤爆は取り返せないが、件数は明日取り返せる。**

#### 落とした理由を、正確に書く

**この工程を足すと窓の作業量は増える。** ただし**「時間切れ」で片付けないこと。**

2026-08-23 の3窓を検証したところ、**「時間切れ」という記述に根拠がなかった。**

| 窓 | ログの記述 | 実際 |
|---|---|---|
| 21:00 | 見出しに「（時間切れ）」 | **根拠の記載なし。** 何に時間を使ったかも書いていない |
| 22:00 | 「時間を note スキと棚卸しの確認に充てた」 | **時間切れではなく、配分の選択** |
| 23:00 | 「候補が枯れた」 | **検索1本しか試していない。** 探していないだけだった |

**「時間切れ」は、いちばん書きやすい言い訳になる。** 検証されないまま前提として使われる
（実際、この3件はメインセッションが「窓は時間が足りない」と結論する根拠になっていた）。

**落とした項目には、次のどれかを必ず書く。**

| **やらなかった** | 他を優先した。**何を優先したかを書く** |
|---|---|
| **探したが無かった** | **試した検索軸を全部列挙する**（3章。X 7軸 / note 4軸） |
| **時間が足りなかった** | **何にどれだけかかったかを書く。** 書けないなら「時間切れ」と書かない |
| **精査で止まった** | 分析担当が `直す` と判定し、直しきれなかった |

**「時間切れ」とだけ書くのは禁止。**

→ **件数が落ちても、精査を飛ばさない。**
**「時間が無いので精査を省いた」も禁止。** 省くくらいなら送らない。

### 投稿前チェック（必ず全部通す）

| チェック | 潰す事故 | 方法 |
|---|---|---|
| **本文の残存** | **本文が入力欄に入っておらず、中身が改行1文字だった**（2026-08-23 21:00窓・送信前に検知） | 送信直前に下書きを読み出し、**文字数と本文の完全一致**を確認する |
| 数字の残存 | 「約10万円」→「約万円」（実際に発生） | 元の文と投稿欄の数字を突き合わせる |
| 誤変換スキャン | 頼む→頑む、癖→癱、諦める→諸める、晩→晚、腑→腐 | 下書きをJSで読み出し `/[晚諸頑癱螢腐]/` で検査 |
| 事実の裏取り | 記事と食い違う投稿 | 数字や主張を出すときは元記事を開いて確認 |

#### 数字は算用数字で書く（2026-08-24 オーナー指摘で修正）

**数字は「3年目」「100回」「900円」と算用数字で書く。**

**半角数字は入力時に脱落することがある**（「約10万円」→「約万円」、「5分」→「分」の実例2件）。
**だから送信前に残存を確認する。** ここまでは変わらない。

**しかし「脱落したら漢数字に切り替える」は誤りだった。**
この回避策が既定の動作になり、**最初から漢数字で書く**運用になっていた。

**実際に起きたこと**: 相手が「一人暮らし**3年目**」と書いたリプに、
こちらが「同じ**三年目**です」と返した。**同じ言葉を、わざわざ違う表記で返している。**
「**三**パターン」「**百**回」も同様。**事故を避けるために、文章を犠牲にしていた。**

**脱落したときの正しい対処**

| 1 | **もう一度入力し直す。** 一度で駄目でも、二度目で入ることがある |
|---|---|
| 2 | 二度目も駄目なら、**入力欄をクリアして最初から打ち直す**（8章「入力欄をクリアするときは」） |
| 3 | それでも駄目なら、**その数字を含む表現を変える**（「5分」→「五分」ではなく「あと少し」など） |
| 4 | **漢数字は最後の手段。** 使ったら日報に「算用数字が入らなかったので漢数字にした」と書く |

**漢数字が自然な言葉は、そのまま漢数字でよい**（一人暮らし／一汁一菜／三日坊主／一番）。
**これは数量ではなく語の一部。** 判断に迷ったら、**相手の書き方に合わせる。**

### フォローバックの判断基準（2026-08-23 21:45 オーナー指示・再変更）

**原則: フォローしてくれた人には、原則すべてフォローバックする。**
除外は**1つだけ**。

| 除外 | **日本語で発信していないアカウント** |
|---|---|

**判定**: bio と直近3投稿を見て、日本語がほぼ無ければ除外。
**国籍ではなく言語で判定する。** 理由: 日本語の暮らし系アカウントなので、日本語を読まない人は
フォローしても記事に辿り着かない。逆に**海外在住の日本語話者はフォロバする**。
日本語で発信していれば、外国籍でもフォロバする。

**「怪しい」による除外は廃止した（2026-08-23 21:45）。**
以前は情報商材・稼ぐ系・無差別フォロー垢を除外していたが、**この条件は使わない。**
以下はすべて**フォロバする**:

- ジャンル違い（スポーツ、ゲーム、趣味など）
- 情報商材・稼ぐ系・副業系（金額訴求があっても可）
- 無差別フォロー垢（フォロー数がフォロワー数の10倍以上でも可）
- 実体が薄いアカウント（投稿ゼロ、bio空、テンプレ量産）
- フォロワーが少ないアカウント

**唯一の留保**: アダルト・なりすまし。**指示は「外国人以外は全員」なのでフォロバはするが、
該当が出たら日報に書く。** フォロー一覧は公開されるため、判断を変える材料になる。
（note の扱いと揃えている）

**迷ったらフォロバする。** フォロワー数の増加を優先する方針のため。

**この基準はこちらから先にフォローする場合には適用しない。** そちらは下の
「こちらから先にフォローしない条件」に従う。**フォロバと自発フォローは別物。**

### note の場合 — 全員フォロバする（2026-08-23 オーナー指示）

**note でフォローしてくれた人は、判定せず全員フォローバックする。**
X のような除外条件（言語・怪しさ）は適用しない。プロフィールも記事も読まなくてよい。

理由: note は既に「フォロバしてくれる人と繋がる」方針で運用しており
（2026-08-19にフォロバなし120件を整理済み）、相互フォローが前提の場になっている。
判定を挟むより、全員に返すほうが方針と一致し、窓の作業も軽い。

**上限なし。** 急増日のみ数日に分けて返す（全員に返す方針は変えない）。

**唯一の例外（オーナー判断待ち）**: アダルトコンテンツを主に投稿しているアカウント。
note のフォロー一覧は公開されるため、こちらのアカウントの見え方に影響する。
2026-08-20 に #一人暮らし の新着先頭で実際に遭遇した実例があるので、可能性はゼロではない。
**現時点の指示は「全員」なので全員フォロバするが、該当が出たら日報で報告すること。**


### こちらから先にフォローしない条件

**ここはこちらから先にフォローする場合の条件。フォローバックには適用しない。**
フォロバの基準は上の「フォローバックの判断基準」に従う。**両者を混同しないこと。**

**X**: bio・固定に勧誘文言（副業／稼げ／月収／不労所得／仮想通貨／FX／投資助言／DMください／LINE@）／
アダルト・裏垢／投稿ゼロか全投稿が同一リンク／フォロー数がフォロワー数の10倍以上／なりすまし

**note**: アダルト記事／アフィまとめ量産（「〇〇おすすめ7選」が並ぶ）／情報商材・稼ぐ系の有料note中心／
記事ゼロ・プロフィール空／企業・店舗の販促アカウント

判断が割れるものは**保留して日報で報告**。迷ったら押さない。

## 6. 停止条件

以下のいずれかで**その日は中断し、翌日は量を1段戻す。** 日報で報告する。

- 制限警告が出た
- いいねが弾かれる
- note でエラーが出る

- **リプへの返信率が直近3日平均の50%未満、これが2窓連続**

シャドウバンは無告知で来る。「警告」を待っていると気づけない。数字で見る。

「2窓連続」にするのは、フォロワー182・1ポスト14〜35impという母数では単発のブレが大きいため。

### impを比較するときは、経過時間を揃える（2026-08-23 追加）

**impは「投稿から3時間後」の値で比較する。3時間経っていないポストは判定に使わない。**

揃えないと、**同じポストが伸びていく曲線を、別々のポストの優劣として読んでしまう。**
2026-08-23に実際に2回の誤警報が出た。

| 誤警報 | 中身 |
|---|---|
| 19:00窓 | 「30分で4impと低い」→ 1時間20分後には8に伸びていた |
| 21:00窓 | 「毎時の3本(5/10/9)が単発(22)を下回る」→ **6時間経過と1時間経過を並べていた。** 1時間に揃えると両方5で差なし |

**当面、impによる停止判定は「判定不能」とする。**
3時間後impの記録は2026-08-24以降しか無く、「直近3日平均」の分母が作れない。
**判定不能と書くほうが、揃っていない数字で判定するより安全。** 分母が3日ぶん揃ってから再開する。

## 8. 技術手順

### 座標クリックを使わない

`getBoundingClientRect()` は CSS px（viewport 960幅）、クリックはスクショ px（1126幅）で、
倍率1.173のズレがある。下に行くほど外れる。**合成イベント列で押す。**

```js
['pointerdown','mousedown','pointerup','mouseup','click']
  .forEach(t => el.dispatchEvent(new MouseEvent(t,{bubbles:true,cancelable:true,view:window})));
```

押下後は必ず状態変化で検証する（aria-label の変化、unlike ボタンの出現、ハートの色）。
**件数が変わらない外れ方は誰も気づけない。**

### 入力欄をクリアするときは、最初から実座標クリックを挟む（2026-08-23 実測）

`cmd+a` → `Delete` が効かず、**旧文が残ったまま新しい文が足されて二重入力になった**
（43字のつもりが85字。2026-08-23の23:00窓。送信前に検知）。
JS の Range 選択でも消えなかった。

**解決した手順**

1. **スクリーンショットを撮り、入力欄の実座標をクリックしてフォーカスを当てる**
2. `cmd+a` → `BackSpace`
3. 文字数がゼロになったことを JS で確認してから入力する

**JS の `dispatchEvent` + `focus()` は compose モーダルでは効かないことがある。**
リプ欄では効くのに compose では効かない。**打ち直しのときは最初から実座標でいく。**

### X の入力欄にフォーカスする

```js
const ce = document.querySelector('div[data-testid^="tweetTextarea"] [contenteditable="true"]');
['pointerdown','mousedown','pointerup','mouseup','click']
  .forEach(t => ce.dispatchEvent(new MouseEvent(t,{bubbles:true,cancelable:true,view:window})));
ce.focus();
```

送信ボタンは `button[data-testid="tweetButtonInline"]` を同じ方式で押す。
送信の成否は**下書きが空になったか**で判定する。

### 改行は shift+Return

type アクションに `\n` を入れても改行にならないことがある。`shift+Return` を使う。

### note のスキ

`aria-label="スキ"` の button に合成イベント列。成否は「スキを取り消す」への変化で確認。
**本文のNG語判定を通してから押す。**

### フォロー解除のボタンは `data-testid` だけで選ばない（2026-08-24 実測・重要）

**`data-testid$="-unfollow"` を持つボタンが、実際には「Subscribe（有料購読の申込）」だった実例がある。**

2026-08-24、@kuromojibui のプロフィールで発生:

| testid | aria-label | 実際の機能 |
|---|---|---|
| `1741603468408942592-unfollow` | **Subscribe to @kuromojibui** | **有料サブスクの申込** |

testid だけで選ぶと**課金フローに入る。** 実際に申込ページへ遷移した（支払いはしていない）。

**必ず `aria-label` を確認する。**

```js
// フォロー解除ボタンの正しい選び方
const btn = [...document.querySelectorAll('button[data-testid$="-unfollow"]')]
  .find(b => /^Following|^フォロー中/.test(b.getAttribute('aria-label')||''));
if (!btn) { /* 解除ボタンが無い。スキップして日報に書く */ }
```

**押す前に必ず aria-label をログに残す。** 何を押したか後から確認できるようにする。

### 購読を有効にしたアカウントは、ボタンの構造が違う（2026-08-24 実測）

| | 通常のアカウント | **購読有効アカウント** |
|---|---|---|
| `data-testid$="-unfollow"` | フォロー解除 | **Subscribe（有料購読）** |
| 本物の解除ボタン | 同上 | **testid なし。`aria-label="Unfollow @..."` の人型アイコン** |

**この人型アイコンは、JSからのクリックに反応しない**（`MouseEvent` / `PointerEvent` / `click()`
のいずれも無効）。**実座標クリックを使う。**

**手順**

1. **スクリーンショットを撮って、人型アイコンの位置を目視で確認する**
2. **一度マウスを別の場所へ移してから**、アイコンの中心をクリックする
   （ホバー状態のままだと反応しないことがある）
3. ボタンが `Follow back` に変われば成功。**確認ダイアログは出ない**

**Subscribe ボタンとは約120px離れている。** 目視で座標を取れば誤爆しない。
**推測座標でクリックしないこと。** 必ずスクリーンショットを見てから押す。

**「Subscribe」「購読」「支払」を含むボタンは、いかなる場合も押さない。**
**課金に関わる操作は、オーナー以外が行ってはならない。**

### note の一覧はページネーション。解除するとページがずれる（2026-08-24 実測）

**note のフォロー/フォロワー一覧は無限スクロールではなくページ送り。** `?page=N` で直接移動できる。
**「もっとみる」ボタンは合成イベントでは動かない。**

**API から取るのがいちばん確実。**

```
/api/v2/creators/{urlname}/followings?page=N
/api/v2/creators/{urlname}/followers?page=N
```

レスポンスの `data.follows[]` に **`isFollowed`（相手→自分）** と
**`isFollowing`（自分→相手）** が入っている。**片思いを機械的に確定できる。**
`data.isLastPage` が true になるまで回す。

**【重要】解除するとリスト全体が縮むため、ページを順に進むと行がずれて取りこぼす。**

→ **処理したら、APIで取り直して残件を確認する。** これを1回やれば取りこぼしがゼロか分かる。
　 2026-08-24 は 281→258（23件）を処理した時点で取り直し、残り9件が全てページ6に
　 集まっていることが分かった。**ページ順に進み続けていたら見逃していた。**

**バックグラウンドのタブでは `setInterval` が大幅に絞られる**（90秒で8回）。
**ループ処理はタイマーに頼らず、ツール呼び出し1回につき1ページ分を処理する形にする。**

### 一覧が長すぎて最後まで読めないときは、DOMではなくAPIから取る

**Xのフォロー/フォロワー一覧は、スクロールでは最後まで読めない。**
2026-08-23に実測: Following 200人のうち **54人で読み込みが停止**し、レンダラが45秒フリーズした。
原因はDOMのノード数。**画面に積み上げる方式に限界がある。**

そして **Xの一覧は新しい順**に並ぶ。つまり**古いフォローほど後ろにある**。
1週間ルールの解除候補は「古いフォロー」なので、**スクロール方式では候補に永久に到達できない。**
「走査54/200」は前進に見えて、**毎日同じ54人を見直しているだけ**になる。

**解決: 通信を傍受して、描画を経由せずにデータを取る。**
同じ問題を note では API 取得で解決済み（2026-08-23の22:00窓で250人全員を取得）。**X も同じ手で解ける。**

```js
// 1) まず傍受を仕掛ける（ページを開く前・リロード前に実行する）
window.__cap = [];
const _f = window.fetch;
window.fetch = async function(...a){
  const r = await _f.apply(this,a);
  const u = (typeof a[0]==='string') ? a[0] : ((a[0]&&a[0].url)||'');
  if(/\/(Following|Followers)\?/.test(u)){
    r.clone().json().then(j=>window.__cap.push(j)).catch(()=>{});
  }
  return r;
};
```

```js
// 2) スクロールする。**DOMは絶対に間引かないこと**
window.scrollBy(0, 3000);
```

**【2026-08-23 実測・重要】DOMの間引きは逆効果だった。**

ノードを削ると `document.body.scrollHeight` が縮む。すると `scrollTo(0, scrollHeight)` が
**すでに読み込み済みの位置に着地**し、**次の読み込みが発火しない。**
実際に `最下部到達: true` のまま5件で停止した（プロフィールには99投稿ある）。

→ **間引かない。`scrollBy` で少しずつ下げる。** 描画の重さは受け入れる。

**【2026-08-23 実測・重要】バックグラウンドのタブはタイマーが絞られる。**

`setInterval(..., 600)` を35秒回して**7回しか実行されなかった**（本来は約58回）。
ブラウザがバックグラウンドタブのタイマーを間引くため。

→ **長い一覧を取るときは `tabs_select` でタブを前面にしてから始める。**
　 取り終えたら元に戻す。

```js
// 3) 傍受した中身から一覧を組み立てる
//    followed_by = その相手がこちらをフォローしているか（＝Follows you バッジと同じ意味）
(function(){
  const out = {};
  const walk = o => {
    if (!o || typeof o !== 'object') return;
    const lg = o.legacy;
    if (lg && lg.screen_name) {
      out[lg.screen_name] = {
        followed_by: !!lg.followed_by,   // true = 相互
        following:   !!lg.following,
        created_at:  lg.created_at
      };
    }
    for (const k in o) walk(o[k]);
  };
  (window.__cap||[]).forEach(walk);
  const all = Object.entries(out);
  return {
    取得数: all.length,
    相互: all.filter(([,v])=>v.followed_by).length,
    フォロバなし: all.filter(([,v])=>!v.followed_by).map(([k])=>k)
  };
})();
```

**注意**

- **`fetch` だけでは足りないことがある。** 傍受数が0のまま増えないときは、
  XHR（`XMLHttpRequest`）で通信している。その場合は `XMLHttpRequest.prototype.open` と
  `send` も同様に差し替えて `responseText` を拾う。**「0件だった」で終わらせない。**
- **傍受は必ずページを読み込む前に仕掛ける。** 読み込み後に仕掛けても、
  すでに飛んだリクエストは捕まえられない。**仕掛けてからリロードする。**
- **レスポンスの構造は変わりうる。** 組み立てる前に `window.__cap[0]` を1件そのまま見て、
  `legacy.screen_name` と `legacy.followed_by` が実在するか確認すること。**無ければ構造を読み直す。**
- **取得はこの方法でよいが、解除は1件ずつ画面で行う。** 3章の「判断と実行を分ける」は変わらない。
  APIで取るのは**候補リストの取得（＝手順1の候補取得）**まで。
- 取得できた総数が Following 数に届かない場合は、**届いた分だけで判断し、残数をログに書く。**
  「全部取れた」と書かない。

- もっともらしい原因が見つかっても、そこで探索を止めない

## 8.5 note記事の作り方と、投稿までの受け渡し（2026-08-24 追加）

### 3人で回す

```
執筆担当（note-writer）      下書きを書く。投稿しない
        ↓ メインセッションが渡す
分析担当（sns-analyst）      精査して「このまま出せる／直してから出す」を判定する。原稿は編集しない
        ↓ 「このまま出せる」になったら
SNS担当（sns-operator）      note に投稿する
```

**この順番を飛ばさない。** 執筆担当が自分で投稿しない。分析担当が原稿を直さない。

**なぜ分けるか**: 書き手と査読者を分けるのが精査の目的。
**査読者が直すと、その修正を誰も見ない。**

### 各自の担当と、やらないこと

| | やること | **やらないこと** |
|---|---|---|
| 執筆担当 | 材料集め・構成案・下書き・推敲 | **投稿しない。体験を捏造しない。価格を決めない** |
| 分析担当 | 精査・可否判定・指摘 | **原稿を編集しない** |
| SNS担当 | 投稿・タグ設定・公開後の確認 | **本文を書き換えない**（誤字も報告に留める） |
| メインセッション | 受け渡し・価格の確認・オーナーへの相談 | — |

### 執筆担当は、調べられることを自分で調べてから聞く（2026-08-24 オーナー指示）

**公開されている情報をオーナーに聞かない。** 調べる手間をオーナーに押し付けることになる。

| **自分で調べる** | 営業時間・定休日・住所・電話番号・食べログの点数・受賞歴・予算帯・支払い方法・予約方法・制限時間・アクセス |
|---|---|
| **オーナーに聞く** | **その人にしか無いもの。** 払った金額・誰と行ったか・何を食べたか・言われた言葉・その場で起きたこと |

**線引きは「検索で出るか」。**

**調べた情報には出所と時点を必ず添える。** 飲食店の価格は変わる。
**2年前のページの価格を、いまの価格として書かない。**
一次ソースで確認できなければ **「確認できなかった」と書いて使わない。**

**調べた結果がオーナーの記憶と食い違ったら、それ自体が書く材料になる。**

### 執筆担当は体験を捏造しない

**このアカウントはオーナーの実生活が土台。** 執筆担当が体験を作ると、
**事実でない記述を公開する**ことになる。有料記事なら尚更。

- 材料（買った物・金額・期間・失敗）は**オーナーから受け取る**
- 足りない箇所は `【要確認: 〜】` を残す。**推測で埋めない**
- **金額・日数・回数を「たぶん」で書かない**

### 文体は記事とポストで2点違う

| | Xのポスト | **note記事** |
|---|---|---|
| 文末 | 常体 | **敬体（です・ます）** |
| 完結 | **させない**（オチをつけない） | **させる**（記事は答えを持って終わる） |

**禁止語と「体験を教訓に翻訳しない」は、記事でも同じく適用する。**

### アイキャッチ（サムネ）は誰が決めるか（2026-08-24 追加）

**note は一覧でタイトルとサムネしか見えない。** ここで開かれなければ本文の質は関係ない。
**にもかかわらず、これまで検証する工程が無かった。**

| 工程 | 誰が |
|---|---|
| 方向性を提案する | 執筆担当 — 何を使うか＋理由を、下書きのメタ情報に書く |
| **分析する** | **分析担当** — **どんなアイキャッチが伸びているかを分析し、案と理由をオーナーに渡す** |
| **作る** | **オーナー**（2026-08-24 指示） |
| 貼る | **SNS担当** — 投稿時に設定する |

**作るのはオーナー。** 分析担当は**何が伸びるかを調べて渡すところまで**で、作らない。
**オーナーがアイキャッチを作ってから、SNS担当が投稿する。** 順番を飛ばさない。

#### 分析担当が渡すもの

1. **伸びている記事のアイキャッチに共通していること**（3点まで）
2. **この記事のアイキャッチはこうすべき、という案**（具体的に。文字を入れるなら文言も）
3. **その理由**（①記事の主張と一致するか ②一覧で他と違って見えるか）
4. **既存の様式を踏襲すべきか、変えるべきか**

記録する項目は9章「note記事カルテ」と、分析担当の定義を参照。

#### 既存の様式（2026-08-24 時点で3本）

| サイズ | **1280×670** |
|---|---|
| 書体 | **明朝体**（Hiragino Mincho ProN / Yu Mincho / Times New Roman） |
| 配色 | **グレー基調のモノトーン**（#dcdde0 / #a4a7ad / #b0b3b9 / #f4f4f6） |
| 構成 | episode番号 → タイトル → サブタイトルの**文字主体** |
| テンプレート | `SNS運用/アイキャッチ/template-episode.html` |

**既存3本はすべて「文字のデザイン」で、写真は使っていない。**

#### 写真を使うか、テンプレートを使うか

**どちらが正しいかは決まっていない。記事ごとに判断する。**

| 写真が向く | **実物が主張そのものになる記事。** 例: 「並のハラミがいちばんうまい」→ その皿の写真 |
|---|---|
| テンプレートが向く | **実物が無い／絵にならない記事。** 例: 「食べログに課金したら」 |

**判断の材料は2つ。**

1. **記事の主張と絵が一致しているか**
2. **一覧に並んだとき、他の記事と違って見えるか**（同じジャンルの記事と並べて確かめる）

**シリーズとしての統一感より、1本ずつ開かれることを優先する。**
ただし**乗り換えるなら意識的に乗り換える。** 気まぐれで混ざるのがいちばん良くない。

#### 変わらないこと

- **インターネットから拾った画像は使わない**（著作権。7章）
- 写真を使うなら**オーナーが撮った実物のみ**
- **投稿時に長辺1600px程度へ縮小する**（実測5MBの原寸は重い）

### 精査の前に、似た内容で伸びている記事を探す（2026-08-24 追加）

**ルールに照らすだけの精査では、「間違っていない記事」にしかならない。読まれる記事にはならない。**

分析担当は原稿を読んだら、**同じテーマで伸びている note 記事を10本以上探す**
（2026-08-24 オーナー指示。以前は2〜3本としていた）。

**3本では「共通点」と「たまたま」の区別がつかない。**
2本に同じ特徴があっても偶然の可能性が高い。**10本あれば「10本中7本」と言える。**

**共通点は必ず数で書く。**「多い」「よく見られる」ではなく **「10本中8本が文字入り。うち6本は白文字」。**
**数で書けないなら、それは共通点ではなく印象。**

**入口を分散させる。** 同じ入口から10本取ると、その入口の偏りがそのまま出る。
ハッシュタグの**人気**（新着ではない）／note の急上昇／同ジャンルの複数タグ／
**うちに近いジャンルのアカウントが書いた記事**。

**除外**: 企業アカウント／PR記事／アフィリエイト目的の「おすすめN選」。

**10本に届かなかったら、届かなかったと書く。** 何本集めたかを必ず記録する。

**9章「note記事カルテ」で分解し、原稿と並べる。**

| 比べる項目 | 見るもの |
|---|---|
| **タイトル** | 字数・型・数字の有無。**原文をそのまま並べる** |
| 導入の3行 | 一覧のプレビューに出る部分 |
| 見出しの数と密度 | 何字ごとに1つか |
| 総字数 | |
| **有料ラインの位置と、直前の一文** | 有料記事の場合。**ここが購入の分かれ目** |
| タグの数 | |

**そのうえで具体案を出す。**

- **タイトルは3案出す**（比較した記事の型を踏まえたもの）
- 構成を変えるべきなら、**どの見出しをどこに動かすか**を名指しする
- 有料ラインを動かすべきなら、**移動先を名指しする**

**ただし原稿は編集しない。案を出すところまで。適用するのは執筆担当。**
理由: 査読者が直すと、その修正を誰も見ない。

**似た記事が見つからなければ「見つからなかった」と書く。** 捻り出さない。

### 公開済み記事との差分を「欠落」と決めつけない（2026-08-24 実測）

**公開した記事は、オーナーが直接編集することがある。**

2026-08-24 に実際に起きた。SNS担当が更新前の突き合わせで **本文58文字の差分3箇所**を見つけ、
**「合成pasteの取りこぼし」と診断して1箇所を復元した。**

**実際は3箇所とも、オーナーが意図的に消したものだった。**
**エージェントがオーナーの編集を取り消していた。**

#### 差分を見つけたときの手順

| 1 | **まず「オーナーが編集した可能性」を疑う。** 技術的な欠落だと決めつけない |
|---|---|
| 2 | **復元しない。** 差分をそのまま列挙して報告する |
| 3 | **どちらが正かはオーナーが決める。** 聞くまで触らない |

**判定の材料**: 段落まるごと・文の末尾がきれいに消えているなら、**人の編集の形。**
技術的な欠落は、**文字化け・途中で切れる・順序が入れ替わる**といった形になりやすい。

**ただし断定できない。だから聞く。**

#### なぜこれが起きたか

SNS担当は**「下書きが正、公開ページは下書きの複製」**という前提で動いていた。
**その前提が成り立つのは、公開直後だけ。** オーナーが読んで直した瞬間に崩れる。

**公開された記事は、こちらの出力ではなく、オーナーの持ち物になる。**

### 見出しと目次を必ず付ける（2026-08-24 オーナー指示）

**すべての note 記事に、見出しと目次を付ける。**

| 見出し | **必ず付ける。** h2（`##`）を基本にする |
|---|---|
| **目次** | **必ず入れる。** note の目次機能を使う。**手打ちの目次は作らない** |
| 目次の位置 | **導入の直後**（本文が始まる前） |

**そして短くする。目安は20〜35字、長くても40字まで（2026-08-24 オーナー指摘で追加）。**

### 文体カルテ（2026-08-23 追加・22:59 詳細化）

**「うまい」「読みやすい」で終わらせない。数えられるものを数える。**

#### ① 行ごとの分解（いちばん重要）

### 型カードにする

```

  1行目「（原文）」 22字 — 結論を先に出す

  3行目「（原文）」  7字 — 箇条書き1

うちで書くなら:
```

**「うちで書くなら」を必ず埋める。** 型の説明だけ渡されても書けない。

### 空回りさせない3つの規則

1. **明日試すことを1つだけ決める** — 複数決めると何も試さない。明日の投稿で検証できる粒度にする
2. **試した結果を翌日記録する** — impを見て効いたか書く。これがないと「分析した気になる」で終わる
3. **発見がない日は「なし」と書く** — 捻り出した観察は嘘になる
4. **1日1エントリ。窓ごとに増やさない。** 同じ日に複数の窓で観測したら、その日のエントリに追記する。
   「明日試すこと」は日をまたいで1つだけ。窓ごとに決め直すと何も検証できない
