### 文体

**2026-08-23、伸びている投稿を分析して全面改訂。オーナー指摘「AI的な口調すぎる」を受けたもの。**

#### 伸びている投稿の型は2つしかない

**A. 言い切る**
> 「自炊＝節約」って思い込み、そろそろ捨てていい（2.1K いいね）
> これが一人暮らしした方がいい理由（7.9K）

**B. 場面をそのまま出す**
> 一人暮らしの特権 / 朝からいきなりステーキできる（1.7K）
> 食洗機回すよって言ってんのに皿を下げてこないから蛍の光を口ずさんだら息子がちょっと急ぎ始めた（4.9K）

**共通点: 書き手が意味づけをしない。** 読み手が勝手に納得する。
**「〜な気がします」で終わる投稿は、伸びているものに一つもない。**

#### うちの癖: 体験を教訓に翻訳してしまう

翻訳した瞬間、誰が書いても同じ文になる。実例（すべて自分が書いたもの）:

| 書いたもの | 何が起きているか |
|---|---|
| 「地味だけど効く気がしてる」 | 効能を抽象語で言い、しかも自信なく濁している |
| 「習慣って気合いじゃなくて動線で決まる気がしています」 | 体験を格言に加工している |
| 「続く仕組みを一つ作る方が結果的に強い」 | 「仕組み」「強い」はコンサルの語彙 |
| 「週に必ず一回楽しみが来るという構造」 | 「構造」と言った時点で体験が消える |
| 「いまの自分には効いています」 | 何がどう変わったのかが一切ない |

#### 禁止語と書き換え

| 使わない | 代わりに |
|---|---|
| 効く／効いてる／効いています | **何が起きたかを書く**「皿を洗わない夜が週5になった」 |
| 仕組み／構造／設計 | **具体物で言う**「食洗機」「洗い桶」「鍋ひとつ」 |
| 〜という状態 | **動詞で言う**「〜してる」 |
| 結果的に／本質的に／根本的に | **削除**（なくても意味が通る） |
| 〜な気がします／〜かもしれません | **言い切る**。言い切れないなら書かない |
| 強い／最適／効率／コスパが良い | **数字か場面に置き換える** |
| 〜のほうが◯◯です（対比構文） | 使ってもよいが1ポストに1回まで |
| **〜する方法を、私は持っていません**（能力の不在を「持っていない」で言う翻訳調） | **その場の言葉で言う**「確かめていません」／**言わずに済ませる** |
| **それで足りました／これで十分です**（指示語だけで受ける締め） | **何が足りたのかを名詞で書く**「1セットで1ヶ月回りました」／**削除** |

**⛔⛔ 上の2つは「型」であって単語ではない（2026-09-10 オーナー指摘）。**
どちらも**段落の最後にもう1文足して締めた文**で、実測したAI感の型B（最後を締めの1文で受ける。他人14%／うち50%）そのもの。

- **見分け方**: その1文を消して、段落が成立するか。**成立するなら、その文はAI感のためだけに在る。**
- **直し方は言い換えではなく「足さない」。** 具体的な事実で終わっている段落に、まとめの1文を付け足さない
- ⛔ 「〜から。」の倒置で締める形（「〜ませんから。」）と、指示語（それ・これ）で受ける短文が2大パターン

#### 書き換えの例

|---|---|

#### 具体的にすることと、分かりやすくすることは別（2026-08-24 オーナー指摘）

**「抽象語を避けて具体物で言え」と書いた結果、具体的だが一読で像が浮かばない表現が出た。**

**オーナーの指摘**:
> **「シンクに渡す折りたたみの板」や「積み立てを先に引いた」など、何を言ってるのかわかりにくい**

| ✕ 分かりにくい | なぜ | ○ こう書く |
|---|---|---|
| シンクに**渡す**折りたたみの板 | 「渡す」が伝わらない。何の板かも不明 | **折りたたみのまな板** |
| 積み立てを**先に引いた** | 「引く」が多義（引き落とし／差し引き／撤退） | **給料日に先に積み立てへ回した** |

#### 3つだけ守る

**1. 一読で絵が浮かぶか。** 浮かばないなら書き直す。**二度読ませない。**

**2. 呼び名がある物は、その呼び名で言う。**
自分で説明句を作らない。「シンクに渡す板」ではなく「まな板」。
**説明句は、書き手には正確に見えて、読み手には初見の言葉になる。**

**3. 多義の動詞を避ける。**
**引く／当てる／回す／かける／出す**は、文脈が薄いと別の意味に読める。
**「積み立てを引く」ではなく「積み立てに回す」。**

#### 具体を捨てるのではない

**抽象語に戻すのではない。**「効く」「仕組み」「構造」は禁止のまま。

**具体的で、かつ一読で分かる言葉**を選ぶ。両立する。
**迷ったら、その物を人に口で説明するときの言い方にする。**
口では「シンクに渡す折りたたみの板」とは言わない。「折りたたみのまな板」と言う。

#### 書く前の自己チェック

1. **禁止語が入っていないか**（効く・仕組み・構造・強い・気がします）
2. **最後の一文が教訓になっていないか。** なっていたら削る。場面で終わらせる
3. **この文、他の誰かが書いても成立しないか。** 成立するなら具体が足りない

#### 完結させない（2026-08-23 追加）

**2026-08-23の4本は、すべて過去形で完結していた。** これが「AIっぽさ」の正体。

| 書いたもの | 文末 |
|---|---|
| 一人暮らしの家電で一番やらかしたのは…音の方**でした** | 過去の総括 |
| はずれの日が減り**ました**／いまの自分には効いてい**ます** | 過去の総括 |
| 洗い物のほう**でした**／やめる工程を決めるほうが効き**ました** | 過去の総括 |

**「もう終わったこと」として語ると、書いたものに見える。**
人間の投稿は進行中の話が多く、**オチが無いまま終わるものが普通にある。**

守ること:

1. **現在形・進行形を基本にする。** いま起きていること、まだ終わっていないことを書く
2. **オチをつけない投稿を混ぜる。** 気づき・教訓で締めない回を作る。言いっぱなしでよい
3. **長さをばらす。** 4本とも3文・70〜120字だった。**1行だけの投稿があっていい**
4. **話し言葉を混ぜる。**「〜してる」（〜しているにしない）「〜なんだけど」「〜って」

## 2.5 起動元の判定（二重稼働の防止）

**X・note に書き込んでよいのは、プロンプトに `起動元=sns-operator-window` を含む起動だけ。**

合言葉がない起動（手動セッションからの `Agent` 呼び出しなど）では、
**読み取りと分析だけを行い、書き込みは一切しない。**

理由: エージェントは自分の起動元を知る手段を持たない。合言葉がないと、正規の窓稼働と
手動起動が区別できず二重稼働が起きる。二重稼働は同じ相手への重複リプ・上限の二重消費を招く。

**メインセッション（設計・記事執筆・週次分析の担当）は、日次リアクションを行わない。**
調査や修正で X を触る必要がある場合は、**窓と窓の間**（各窓の起動から75分を過ぎ、次の窓の起動前まで）に行う。

### 会話にひもづくいいね（2026-08-23 オーナー指示）

**リプのやり取りに関係する投稿には、例外なくいいねを押す。**

| 対象1 | **自分宛に来たリプ** — 返信するかどうかに関わらず、全部にいいねする |
|---|---|
| 対象2 | **自分がリプを送るポスト** — リプを送るなら、その元ポストにも必ずいいねする |

**この2つは3章の精査プロセスを別途走らせなくてよい。**
理由: どちらも**返信を書くために本文を読んでいる**ので、精査の実質（1件ずつ読む）が
すでに済んでいる。読まずに押しているわけではない。

**1日のいいね上限（50件）には数えない。** 上限は「探しに行って押す分」を抑えるための枠で、
会話の中で押す分は性質が違う。リプへの返信を上限から外したのと同じ考え方。

#### ⛔ 数えるか数えないかは「誰を押したか」ではなく「どのパイプラインから出た1件か」で決める（2026-09-01 追記）

**2026-09-01 に、窓ごとに数え方が食い違った**（9:00窓は枠に数えず、18:00・20:00窓は数えた）。
**原因は「リプを送った相手だから会話ぶん」と、相手で判定したこと。** 正しい判定はこうである。

| **枠に数える** | **いいね候補の検索軸から出て、3章の精査を通って押した分**（＝探しに行った分）。**その相手にあとからリプも送ったかどうかは関係ない** |
|---|---|
| **枠に数えない** | **上の対象1・対象2**。＝**その1件が、リプがなければ存在しなかった場合だけ** |

**⛔ 相手で数えると、いいね軸が正規に拾った1件まで枠から消えて、枠が実態より緩む。**
上限は緩むほうが危険（＝制限に触れる方向）なので、**迷ったら「数える」側に倒す。**

**具体例（2026-09-01 実測）**
- **リプ候補として探して押したが、精査が落としてリプを送らなかった** → **数える**（対象2は「リプを送るなら」なので当たらない）
- **いいね軸から出て押し、あとで同じ相手にリプも送った** → **数える**（出自がいいね軸）
- **リプを送るために元ポストを開いて押した** → **数えない**（対象2そのもの）

**⭐ ログの書式**: いいねの内訳表に **「軸から◯件／会話ぶん◯件（枠外）」を必ず分けて書く。**
20:00窓がこれを分けて書いていたので、あとから再計算できた。**合計だけ書くと訂正できない。**

**唯一の留保**: 相手のリプが 3章の足切り（アダルト・勧誘・闘病・訃報など）に当たる内容だった場合も、
指示は「全て」なのでいいねはする。ただし**該当が出たら日報に書く。** 判断を変える材料になる。

### 会話を締める挨拶には返信しない（2026-08-23 オーナー指示）

「ありがとうございます」「参考になりました」など、**会話を終える合図の挨拶には返信しない。**
返すと相手に再返信の義務感を作り、やり取りが終われなくなる。

**ただし、いいねは押す**（上の「対象1」に含まれる）。
無視ではなく「受け取った」という合図を、いいねの側で返す。

### 取り消し

精査をすり抜けた場合の最後の手段。使ったら**ログに「なぜ精査で防げなかったか」を書く。**
書かないと同じ穴が塞がらない。

## 4. ポスト

### 大原則: 予約も作り置きもしない

- **X の予約投稿機能は使わない**
- **ストックを作って消化する運用もしない**
- ポストは**その窓で分析して、その窓で書いて、その窓で出す**

理由: 作り置きは書いた時点の情報で止まる。前の窓で何が伸びたか、いま何が話題かを
反映できないので、改善が回らない。**毎回考えて書くことが改善の前提。**

### 分析と改善のループ

全部に重い分析はかけない。粒度を分ける。（⭐ 2026-09-17 更新: ~~9本~~ → **5本**・~~朝4:30~~ → **朝3:00**）

| タイミング | 頻度 | やること |
|---|---|---|
| **朝（3:00）** | 1日1回・重め | **分析担当**が `分析ブリーフ.md` を書く。SNS担当は読むだけ |
| **毎ポスト前** | 5回・軽め | ブリーフを見てから書く。**⛔ 「投稿3時間後のimp」を見て判断しない**（2026-09-10 廃止。齢3時間の値は優劣を分けない） |
| **毎ポスト後** | 5回 | **何を狙って書いたかを1行**でログに残す |
| **次の窓** | 5回 | 前のポストのimpを拾い、狙いが当たったか記録 |

#### ⛔⛔ ブリーフは「他人から借りた型」を渡さない（2026-09-17 ルール化・**5窓連続で使われなかった**）

**事実（9/16）**: ブリーフが渡した型を、**5窓すべてが「使っていない」と記録した。理由も5回とも同じ**で、
**「精査（分析担当）の直し案が、その形ではなかったため」。**

**⛔ これは SNS担当には直せない。**型は**朝に、他人の投稿から**作られ、精査は**窓の中で、その1本の事実関係と重複から**直す。
**同じ分析担当の中で、朝の自分が渡した型を、窓の中の自分が精査で消していた。**

| **⛔ やらない** | 精査の項目に「ブリーフの型に合っているか」を足すこと。**型が外部由来である限り事実関係の直しと毎回衝突し、⛔ 衝突したら事実が勝つべきなので、精査が弱くなる** |
|---|---|
| **⭕ やる** | ブリーフが渡すのは**「精査が実際に通した形」**。**うちの送信済みポストから抽出する**（例 9/16 の4本: 物か事実から入る → 具体を1〜2個 → 最後は自分の小さな引っかかりで止める） |

**⭐ 他人の型カードは `ベンチマーク.md` に残す。**観測をやめるのではなく、**ブリーフで窓に渡すのをやめる。**

### 「狙い」を必ず書く

これが改善の起点。狙いを書かずに出すと、伸びても伸びなくても**なぜかが分からない**。

例: 「1文完結・オチを最後に置く型を試す」「数字を冒頭に置いて引きを作る」
「問いかけで始めてリプを誘う」「時事に絡めて検索流入を狙う」

1行でよい。書かないポストは改善に寄与しないので、書けないなら出さない。

### ポストは2時間に1本（2026-08-23 23:01 オーナー決定・**2026-08-30 の8窓化で窓割りを更新**）

「2時間に1本」の原則は変えない。5窓体制（2026-09-04〜）は窓間隔が3〜5時間なので、**全5窓でポストしてよい**。

| ポストする窓 | 7:00 / 12:00 / 15:00 / 18:00 / 22:00（すべて） |
|---|---|

**1日5本**（＋タグ投稿1本の別枠で計6本）。17窓時代は9本＋1本、7窓時代は7本＋1本、3窓時代は3本＋1本だった。
**⛔ 面（体験・note誘導・時事）の配分は毎朝ブリーフで決め直す。**
**⭐ 本数を戻した根拠は日次impの実測**（0本=53／3本=167・356／5本=257／6本=290・336／7本=427・457）。7本まで頭打ちの兆候は無いが、6本・7本は各n=2で差を判定できないため5本で止めている。**再判定は 2026-09-11。**

### 送る前に、分析担当の精査を通す（2026-08-24 オーナー指示）

#### 呼び出す形で行う

1件ごとに呼ぶと、窓が終わらない。

**誤爆は取り返せないが、件数は明日取り返せる。**

#### 数字は算用数字で書く（2026-08-24 オーナー指摘で修正）

**数字は「3年目」「100回」「900円」と算用数字で書く。**

**半角数字は入力時に脱落することがある**（「約10万円」→「約万円」、「5分」→「分」の実例2件）。
**だから送信前に残存を確認する。** ここまでは変わらない。

**しかし「脱落したら漢数字に切り替える」は誤りだった。**
この回避策が既定の動作になり、**最初から漢数字で書く**運用になっていた。

**実際に起きたこと**: 相手が「一人暮らし**3年目**」と書いたリプに、
こちらが「同じ**三年目**です」と返した。**同じ言葉を、わざわざ違う表記で返している。**
「**三**パターン」「**百**回」も同様。**事故を避けるために、文章を犠牲にしていた。**

**脱落したときの正しい対処**

| 1 | **もう一度入力し直す。** 一度で駄目でも、二度目で入ることがある |
|---|---|

### 座標クリックを使わない

`getBoundingClientRect()` は CSS px（viewport 960幅）、クリックはスクショ px（1126幅）で、
倍率1.173のズレがある。下に行くほど外れる。**合成イベント列で押す。**

```js
['pointerdown','mousedown','pointerup','mouseup','click']
  .forEach(t => el.dispatchEvent(new MouseEvent(t,{bubbles:true,cancelable:true,view:window})));
```

押下後は必ず状態変化で検証する（aria-label の変化、unlike ボタンの出現、ハートの色）。
**件数が変わらない外れ方は誰も気づけない。**

### 入力欄をクリアするときは、最初から実座標クリックを挟む（2026-08-23 実測）

`cmd+a` → `Delete` が効かず、**旧文が残ったまま新しい文が足されて二重入力になった**
（43字のつもりが85字。2026-08-23の23:00窓。送信前に検知）。
JS の Range 選択でも消えなかった。

**解決した手順**

1. **スクリーンショットを撮り、入力欄の実座標をクリックしてフォーカスを当てる**
2. `cmd+a` → `BackSpace`
3. 文字数がゼロになったことを JS で確認してから入力する

**JS の `dispatchEvent` + `focus()` は compose モーダルでは効かないことがある。**
リプ欄では効くのに compose では効かない。**打ち直しのときは最初から実座標でいく。**

### X の入力欄にフォーカスする

```js
const ce = document.querySelector('div[data-testid^="tweetTextarea"] [contenteditable="true"]');
['pointerdown','mousedown','pointerup','mouseup','click']
  .forEach(t => ce.dispatchEvent(new MouseEvent(t,{bubbles:true,cancelable:true,view:window})));
ce.focus();
```

送信ボタンは `button[data-testid="tweetButtonInline"]` を同じ方式で押す。
送信の成否は**下書きが空になったか**で判定する。

### 改行は shift+Return

type アクションに `\n` を入れても改行にならないことがある。`shift+Return` を使う。

### note のスキ

`aria-label="スキ"` の button に合成イベント列。成否は「スキを取り消す」への変化で確認。
**本文のNG語判定を通してから押す。**

### フォロー解除のボタンは `data-testid` だけで選ばない（2026-08-24 実測・重要）

**`data-testid$="-unfollow"` を持つボタンが、実際には「Subscribe（有料購読の申込）」だった実例がある。**

2026-08-24、@kuromojibui のプロフィールで発生:

| testid | aria-label | 実際の機能 |
|---|---|---|
| `1741603468408942592-unfollow` | **Subscribe to @kuromojibui** | **有料サブスクの申込** |

testid だけで選ぶと**課金フローに入る。** 実際に申込ページへ遷移した（支払いはしていない）。

**必ず `aria-label` を確認する。**

```js
// フォロー解除ボタンの正しい選び方
const btn = [...document.querySelectorAll('button[data-testid$="-unfollow"]')]
  .find(b => /^Following|^フォロー中/.test(b.getAttribute('aria-label')||''));
if (!btn) { /* 解除ボタンが無い。スキップして日報に書く */ }
```

**押す前に必ず aria-label をログに残す。** 何を押したか後から確認できるようにする。

### 購読を有効にしたアカウントは、ボタンの構造が違う（2026-08-24 実測）

| | 通常のアカウント | **購読有効アカウント** |
|---|---|---|
| `data-testid$="-unfollow"` | フォロー解除 | **Subscribe（有料購読）** |
| 本物の解除ボタン | 同上 | **testid なし。`aria-label="Unfollow @..."` の人型アイコン** |

**この人型アイコンは、JSからのクリックに反応しない**（`MouseEvent` / `PointerEvent` / `click()`
のいずれも無効）。**実座標クリックを使う。**

**手順**

1. **スクリーンショットを撮って、人型アイコンの位置を目視で確認する**
2. **一度マウスを別の場所へ移してから**、アイコンの中心をクリックする
   （ホバー状態のままだと反応しないことがある）
3. ボタンが `Follow back` に変われば成功。**確認ダイアログは出ない**

**Subscribe ボタンとは約120px離れている。** 目視で座標を取れば誤爆しない。
**推測座標でクリックしないこと。** 必ずスクリーンショットを見てから押す。

**「Subscribe」「購読」「支払」を含むボタンは、いかなる場合も押さない。**
**課金に関わる操作は、オーナー以外が行ってはならない。**

### note の一覧はページネーション。解除するとページがずれる（2026-08-24 実測）

**note のフォロー/フォロワー一覧は無限スクロールではなくページ送り。** `?page=N` で直接移動できる。
**「もっとみる」ボタンは合成イベントでは動かない。**

**API から取るのがいちばん確実。**

```
/api/v2/creators/{urlname}/followings?page=N
/api/v2/creators/{urlname}/followers?page=N
```

レスポンスの `data.follows[]` に **`isFollowed`（相手→自分）** と
**`isFollowing`（自分→相手）** が入っている。**片思いを機械的に確定できる。**
`data.isLastPage` が true になるまで回す。

**【重要】解除するとリスト全体が縮むため、ページを順に進むと行がずれて取りこぼす。**

→ **処理したら、APIで取り直して残件を確認する。** これを1回やれば取りこぼしがゼロか分かる。
　 2026-08-24 は 281→258（23件）を処理した時点で取り直し、残り9件が全てページ6に
　 集まっていることが分かった。**ページ順に進み続けていたら見逃していた。**

**バックグラウンドのタブでは `setInterval` が大幅に絞られる**（90秒で8回）。
**ループ処理はタイマーに頼らず、ツール呼び出し1回につき1ページ分を処理する形にする。**

### Bash で `cd A && B` を書かない（2026-08-24・止まる原因）

**`cd` を含む複合コマンドは、権限設定に関係なく必ず許可を求められます。**
`Compound command contains cd with write operation - manual approval required` と出て止まります。
**⚠ 2026-08-24 23:45 訂正: これは「手動」モードでの話です。**
**`bypassPermissions` では、`cd` を含む複合コマンドも確認なしで実行されます**
（22:00窓の45件で実測。拒否ゼロ）。**窓は bypassPermissions で動くので、実害はありません。**

**それでも絶対パスで書くほうが安全です。** モードが変わったときに止まらずに済みます。

**必ず絶対パスで書いてください。**

| ✕ 止まる | `cd "/Users/kyoichi/Claud用/SNS運用" && grep -n "見出し" 運用ルール.md` |
|---|---|
| **○ 通る** | `grep -n "見出し" "/Users/kyoichi/Claud用/SNS運用/運用ルール.md"` |

**`;` で繋いだ複合コマンドも止まりやすい。** 1コマンド1回に分けてください。
**呼び出し回数が増えても、許可待ちで止まるより速い。**

### 一覧が長すぎて最後まで読めないときは、DOMではなくAPIから取る

**Xのフォロー/フォロワー一覧は、スクロールでは最後まで読めない。**
2026-08-23に実測: Following 200人のうち **54人で読み込みが停止**し、レンダラが45秒フリーズした。
原因はDOMのノード数。**画面に積み上げる方式に限界がある。**

そして **Xの一覧は新しい順**に並ぶ。つまり**古いフォローほど後ろにある**。
1週間ルールの解除候補は「古いフォロー」なので、**スクロール方式では候補に永久に到達できない。**
「走査54/200」は前進に見えて、**毎日同じ54人を見直しているだけ**になる。

**解決: 通信を傍受して、描画を経由せずにデータを取る。**
同じ問題を note では API 取得で解決済み（2026-08-23の22:00窓で250人全員を取得）。**X も同じ手で解ける。**

```js
// 1) まず傍受を仕掛ける（ページを開く前・リロード前に実行する）
window.__cap = [];
const _f = window.fetch;
window.fetch = async function(...a){
  const r = await _f.apply(this,a);
  const u = (typeof a[0]==='string') ? a[0] : ((a[0]&&a[0].url)||'');
  if(/\/(Following|Followers)\?/.test(u)){
    r.clone().json().then(j=>window.__cap.push(j)).catch(()=>{});
  }
  return r;
};
```

```js
// 2) スクロールする。**DOMは絶対に間引かないこと**
window.scrollBy(0, 3000);
```

**【2026-08-23 実測・重要】DOMの間引きは逆効果だった。**

ノードを削ると `document.body.scrollHeight` が縮む。すると `scrollTo(0, scrollHeight)` が
**すでに読み込み済みの位置に着地**し、**次の読み込みが発火しない。**
実際に `最下部到達: true` のまま5件で停止した（プロフィールには99投稿ある）。

→ **間引かない。`scrollBy` で少しずつ下げる。** 描画の重さは受け入れる。

**【2026-08-23 実測・重要】バックグラウンドのタブはタイマーが絞られる。**

`setInterval(..., 600)` を35秒回して**7回しか実行されなかった**（本来は約58回）。
ブラウザがバックグラウンドタブのタイマーを間引くため。

→ **長い一覧を取るときは `tabs_select` でタブを前面にしてから始める。**
　 取り終えたら元に戻す。

```js
// 3) 傍受した中身から一覧を組み立てる
//    followed_by = その相手がこちらをフォローしているか（＝Follows you バッジと同じ意味）
(function(){
  const out = {};
  const walk = o => {
    if (!o || typeof o !== 'object') return;
    const lg = o.legacy;
    if (lg && lg.screen_name) {
      out[lg.screen_name] = {
        followed_by: !!lg.followed_by,   // true = 相互
        following:   !!lg.following,
        created_at:  lg.created_at
      };
    }
    for (const k in o) walk(o[k]);
  };
  (window.__cap||[]).forEach(walk);
  const all = Object.entries(out);
  return {
    取得数: all.length,
    相互: all.filter(([,v])=>v.followed_by).length,
    フォロバなし: all.filter(([,v])=>!v.followed_by).map(([k])=>k)
  };
})();
```

**注意**

- **`fetch` だけでは足りないことがある。** 傍受数が0のまま増えないときは、
  XHR（`XMLHttpRequest`）で通信している。その場合は `XMLHttpRequest.prototype.open` と
  `send` も同様に差し替えて `responseText` を拾う。**「0件だった」で終わらせない。**
- **傍受は必ずページを読み込む前に仕掛ける。** 読み込み後に仕掛けても、
  すでに飛んだリクエストは捕まえられない。**仕掛けてからリロードする。**
- **レスポンスの構造は変わりうる。** 組み立てる前に `window.__cap[0]` を1件そのまま見て、
  `legacy.screen_name` と `legacy.followed_by` が実在するか確認すること。**無ければ構造を読み直す。**
- **取得はこの方法でよいが、解除は1件ずつ画面で行う。** 3章の「判断と実行を分ける」は変わらない。
  APIで取るのは**候補リストの取得（＝手順1の候補取得）**まで。
- 取得できた総数が Following 数に届かない場合は、**届いた分だけで判断し、残数をログに書く。**
  「全部取れた」と書かない。

### ⭐⭐ note の全体ビューは `total_pv` を読む。記事別を足し算しない（2026-09-17 ルール化）

**⛔ `/api/v1/stats/pv` の `note_stats` は1ページ12本。** 13本目からは2ページ目に落ちる。
**記事別を足すと、2ページ目が丸ごと抜けたまま「それらしく増える合計」が出る。**

**実害**: 9/10 公開のゴミ箱記事が13本目だったため、**9/11〜9/13 の台帳の note view が3日間ずれていた**
（例 9/13: 台帳 1,669 ／ 正 `total_pv` 1,707）。**⛔ 件数が変わらない外れ方なので、誰も気づけない。**

**⭕ 同じ応答の `data.total_pv` を読む。**ページ数に左右されない。
**⭐ 過去日も遡れる**: `end_date=YYYY-MM-DD` を付ければ、その日に取り損ねても後から確定値が取れる。

### ⭐⭐ 「取れない」と書く前に、返ってきた型（キー）を1度全部出す（2026-09-17 ルール化）

**⛔ 実例**: 「リンククリックは取得手段が無い」と7日以上書いていたが、**誤り**だった。
`accountOverviewDailyQuery` の `engagement_type` に **`Url` としてずっと入っていた。**
**⛔ 見えなかった理由は単純で、この API は値が 0 の型を配列ごと返さない。0 が続く型は存在しないように見える。**

| **⛔ 危ないパターン** | 「探したが見つからない」→「取得手段が無い」と書く。**実際は「まだ 0 なので出てこない」だけ** |
|---|---|
| **⭕ 対策** | 探している項目名で探すのをやめ、**返ってきた全部の型を一覧で出す**。`[...new Set(arr.map(s=>s.engagement_type))]` の1行で済む |
| **⭕ もう1つ** | **「取れない」と書いた日を必ず併記する。⛔ 7日たったら1度だけ取り直す。**台帳の「取れない」は放っておくと何日でも残る |

**⭐ 一般則。X の API に限らない。**（記憶 `blocked-observer`「原因が原因自身を隠す」と同じ型）

### 不調時の復旧

- X のモーダル（compose・予約投稿）が壊れることがある。**ホームのインライン入力欄なら動く**
- タブが応答しなくなったら新規タブを作って旧タブを閉じる
- `Runtime.evaluate` がタイムアウトしたら同URLへ `force: true` で再navigate

### UIが空に見えるとき、壊れているとは限らない

X の予約投稿一覧が空で描画されたとき「モーダルが壊れている」と誤診した実例がある。
実際は予約がゼロで、空状態の描画が不完全なだけだった。

**「表示されない」と「データが無い」を区別する。** 通信を横取りしてレスポンスを直接読む。

```js
const of = window.fetch;
window.fetch = async function(...a){
  const r = await of.apply(this,a);
  const u = (typeof a[0]==='string') ? a[0] : (a[0]&&a[0].url)||'';
  if (/対象のAPI名/.test(u)) r.clone().text().then(t => { window.__cap = t });
  return r;
};
```
XHR を使う画面もあるので `XMLHttpRequest.prototype.open/send` も同様にフックする。
フックを仕込んでから画面を操作し直すと、レスポンス本文が `window.__cap` に入る。

**投稿の正確なタイムスタンプを `time[datetime]` 属性から取る。**

- **毎時ちょうど（:00:0x）の投稿は、予約投稿の発火を第一に疑う**
- **「裏取り済み」と書くときは、裏を取った対象が結論そのものか確認する。**
  周辺事実（別プロセスが動いていた）の確認を、結論（だから投稿した）の証明にすり替えない
- もっともらしい原因が見つかっても、そこで探索を止めない

### タブは使い終わったら毎回閉じる（2026-08-30 オーナー指示）

**使わない X・note のタブを残さない。** オーナーの Chrome が SNS 運用のタブで埋まる。

| 窓の途中 | そのタブでの用が済んだ時点で `tabs_close_mcp` で閉じる。**同時に開いていてよいのは、いま操作している1枚だけ** |
|---|---|
| 窓の終わり | **残っているタブを全部閉じてから窓を閉じる。**ログを書く前に `tabs_context_mcp` で0枚を確認する |
| 例外 | なし。次の窓に渡すために残すことはしない |

**⛔ これは「復旧したタブは窓の終わりに閉じない」（8/30 22:00窓）を上書きする。**
あの手順は暖機のやり直し（約10分）を避けるためだったが、オーナーの判断で**暖機コストを払ってでも閉じる**。
タブがゼロ枚なのは異常ではない（次節）。ログインも消えない。

**閉じ忘れの検出:** 窓の終わりの `tabs_context_mcp` が1枚でも返したら、閉じてからログを書く。
「たぶん閉じた」で通さない — 残るのは静かな形の失敗で、次の窓では気づけない。

**⭐ 窓ごとにタブグループが増える。** 窓は毎回そのセッション専用のグループを作るので、
閉じ漏れると「Sns operator window」というグループが**窓の数だけ Chrome に積み上がる**
（2026-08-30 実測: 4グループ・X タブ5枚が残っていた）。

| 全部閉じた | タブ0枚 → **Chrome がグループごと自動で消す** → タブバーに何も残らない |
|---|---|
| 閉じ漏れた | グループのラベルが残る。**これが唯一の目視サイン** |

**⛔ 他の窓が残したグループは、後の窓からは閉じられない。** MCP は自分のセッションのグループしか触れず、
computer-use もブラウザは読み取り専用。**残骸の掃除はオーナーの手作業になる**
（グループ名を右クリック →「グループを閉じる」）。だから自分の窓は自分で閉じ切ること。

### タブがゼロ枚のときの復帰（2026-08-23 実測）

**窓の開始時、タブが1枚も無いことがある。** 前の窓が片付けて終わると、

|---|---|
| **やってはいけない** | `tabs_create_mcp` を先に呼ぶ。**ゼロ枚からは失敗する**（「グループが存在しない」エラー） |

**ログインは消えない。** X・note の認証は Chrome の Cookie にあり、タブとは独立している。
タブがゼロでも、開き直せばログイン済みで表示される（2026-08-23 に実測確認）。


## 8.4 ⛔⛔ 送信前に「過去の送信文」と「材料台帳」を機械照合する（2026-09-10 ルール化・**実例5件**）

**ポスト・リプを送る前に、必ず次の2つを引く。目で見て思い出すのではなく、機械で引く。**

| **1** | **過去の送信文との重複**: `SNS運用/ログ/*.md` を `grep` して、**同じ材料・同じ言い回しを送っていないか**を確認する。<br>**⛔ 12字ずらした程度の書き換えは「別の文」ではない。**冒頭12字だけでなく、**中心の事実（商品名・値段・場面）で引く** |
|---|---|
| **2** | **材料台帳との照合**: `SNS運用/材料台帳.md` の再使用禁止リストを引く。**⛔ 禁止済みの材料を使わない** |

**⭐⭐ 材料台帳の誤りを見つけたら、ログに書かず `申し送り/` に1枚置く（2026-09-17 ルール化・⛔ 同じ型が3回）**

**⛔ 実例**: SNS担当が `ログ/2026-09-10.md` 774行で「材料台帳8章の記述は 8/24 にオーナーが訂正済み」と書き、
**「分析担当へ: 台帳の該当行に訂正を追記してください」**と頼んでいた。
**⛔ 分析担当は読み落とし、誤りは6日間台帳に残り、9/16 にその材料で完成文を1本書いてしまった**（照合の段で気づいた）。

## 8.5 note記事の作り方と、投稿までの受け渡し（2026-08-24 追加）

### 3人で回す

```
執筆担当（note-writer）      下書きを書く。投稿しない
        ↓ メインセッションが渡す
分析担当（sns-analyst）      精査して「このまま出せる／直してから出す」を判定する。原稿は編集しない
        ↓ 「このまま出せる」になったら
SNS担当（sns-operator）      note に投稿する
```

**この順番を飛ばさない。** 執筆担当が自分で投稿しない。分析担当が原稿を直さない。

**なぜ分けるか**: 書き手と査読者を分けるのが精査の目的。
**査読者が直すと、その修正を誰も見ない。**

### アイキャッチ（サムネ）は誰が決めるか（2026-08-24 追加）

**note は一覧でタイトルとサムネしか見えない。** ここで開かれなければ本文の質は関係ない。
**にもかかわらず、これまで検証する工程が無かった。**

| 工程 | 誰が |
|---|---|
| 方向性を提案する | 執筆担当 — 何を使うか＋理由を、下書きのメタ情報に書く |
| **分析する** | **分析担当** — **どんなアイキャッチが伸びているかを分析し、案と理由をオーナーに渡す** |
| **作る** | **オーナー**（2026-08-24 指示） |
| 貼る | **SNS担当** — 投稿時に設定する |

**作るのはオーナー。** 分析担当は**何が伸びるかを調べて渡すところまで**で、作らない。
**オーナーがアイキャッチを作ってから、SNS担当が投稿する。** 順番を飛ばさない。

#### 分析担当が渡すもの

1. **伸びている記事のアイキャッチに共通していること**（3点まで）
2. **この記事のアイキャッチはこうすべき、という案**（具体的に。文字を入れるなら文言も）
3. **その理由**（①記事の主張と一致するか ②一覧で他と違って見えるか）
4. **既存の様式を踏襲すべきか、変えるべきか**

記録する項目は9章「note記事カルテ」と、分析担当の定義を参照。

#### 既存の様式（2026-08-24 時点で3本）

| サイズ | **1280×670** |
|---|---|
| 書体 | **明朝体**（Hiragino Mincho ProN / Yu Mincho / Times New Roman） |
| 配色 | **グレー基調のモノトーン**（#dcdde0 / #a4a7ad / #b0b3b9 / #f4f4f6） |

| テンプレート | `SNS運用/アイキャッチ/template-episode.html` |

**既存3本はすべて「文字のデザイン」で、写真は使っていない。**

#### 写真を使うか、テンプレートを使うか

**どちらが正しいかは決まっていない。記事ごとに判断する。**

| 写真が向く | **実物が主張そのものになる記事。** 例: 「並のハラミがいちばんうまい」→ その皿の写真 |
|---|---|
| テンプレートが向く | **実物が無い／絵にならない記事。** 例: 「食べログに課金したら」 |

**判断の材料は2つ。**

1. **記事の主張と絵が一致しているか**
2. **一覧に並んだとき、他の記事と違って見えるか**（同じジャンルの記事と並べて確かめる）

**シリーズとしての統一感より、1本ずつ開かれることを優先する。**
ただし**乗り換えるなら意識的に乗り換える。** 気まぐれで混ざるのがいちばん良くない。

### 精査の前に、似た内容で伸びている記事を探す（2026-08-24 追加）

**ルールに照らすだけの精査では、「間違っていない記事」にしかならない。読まれる記事にはならない。**

分析担当は原稿を読んだら、**同じテーマで伸びている note 記事を10本以上探す**
（2026-08-24 オーナー指示。以前は2〜3本としていた）。

**3本では「共通点」と「たまたま」の区別がつかない。**
2本に同じ特徴があっても偶然の可能性が高い。**10本あれば「10本中7本」と言える。**

**共通点は必ず数で書く。**「多い」「よく見られる」ではなく **「10本中8本が文字入り。うち6本は白文字」。**
**数で書けないなら、それは共通点ではなく印象。**

**入口を分散させる。** 同じ入口から10本取ると、その入口の偏りがそのまま出る。
ハッシュタグの**人気**（新着ではない）／note の急上昇／同ジャンルの複数タグ／
**うちに近いジャンルのアカウントが書いた記事**。

**除外**: 企業アカウント／PR記事／アフィリエイト目的の「おすすめN選」。

**10本に届かなかったら、届かなかったと書く。** 何本集めたかを必ず記録する。

**9章「note記事カルテ」で分解し、原稿と並べる。**

| 比べる項目 | 見るもの |
|---|---|
| **タイトル** | 字数・型・数字の有無。**原文をそのまま並べる** |
| 導入の3行 | 一覧のプレビューに出る部分 |
| 見出しの数と密度 | 何字ごとに1つか |
| 総字数 | |
| **有料ラインの位置と、直前の一文** | 有料記事の場合。**ここが購入の分かれ目** |
| タグの数 | |

**そのうえで具体案を出す。**

- **タイトルは3案出す**（比較した記事の型を踏まえたもの）
- 構成を変えるべきなら、**どの見出しをどこに動かすか**を名指しする
- 有料ラインを動かすべきなら、**移動先を名指しする**

**ただし原稿は編集しない。案を出すところまで。適用するのは執筆担当。**
理由: 査読者が直すと、その修正を誰も見ない。

**似た記事が見つからなければ「見つからなかった」と書く。** 捻り出さない。

### 公開済み記事との差分を「欠落」と決めつけない（2026-08-24 実測）

**公開した記事は、オーナーが直接編集することがある。**

2026-08-24 に実際に起きた。SNS担当が更新前の突き合わせで **本文58文字の差分3箇所**を見つけ、
**「合成pasteの取りこぼし」と診断して1箇所を復元した。**

**実際は3箇所とも、オーナーが意図的に消したものだった。**
**エージェントがオーナーの編集を取り消していた。**

#### 差分を見つけたときの手順

| 1 | **まず「オーナーが編集した可能性」を疑う。** 技術的な欠落だと決めつけない |
|---|---|
| 2 | **復元しない。** 差分をそのまま列挙して報告する |
| 3 | **どちらが正かはオーナーが決める。** 聞くまで触らない |

**判定の材料**: 段落まるごと・文の末尾がきれいに消えているなら、**人の編集の形。**
技術的な欠落は、**文字化け・途中で切れる・順序が入れ替わる**といった形になりやすい。

**ただし断定できない。だから聞く。**

**その前提が成り立つのは、公開直後だけ。** オーナーが読んで直した瞬間に崩れる。

**公開された記事は、こちらの出力ではなく、オーナーの持ち物になる。**

### 見出しと目次を必ず付ける（2026-08-24 オーナー指示）

**すべての note 記事に、見出しと目次を付ける。**

| 見出し | **必ず付ける。** h2（`##`）を基本にする |
|---|---|
| **目次** | **必ず入れる。** note の目次機能を使う。**手打ちの目次は作らない** |
| 目次の位置 | **導入の直後**（本文が始まる前） |

**手打ちの目次を作らない理由**: 見出しを直したときに目次が古いまま残る。
**note の目次機能なら自動で追従する。**

#### 目次があると、見出しの役割が変わる

**目次は記事の冒頭に一覧で表示される。** つまり**見出しがそのまま「読むかどうかの判断材料」になる。**

**見出しを飾りにしない。目次に並べたときに読ませる形にする。**

**そして短くする。目安は全角15〜25文字、長くても30文字まで**
**（2026-08-24 オーナー指摘で追加。同日、数え方の誤りを訂正）。**

**必ず「文字数」で数える。バイト数ではない。**
日本語1文字は UTF-8 で3バイトなので、**バイト数で数えると3倍に見える。**
`wc -m` はロケールによってバイト数を返すことがある。**`python3 -c "print(len('…'))"` で数えること。**

**「読ませる形」と「短い」は両立する。短いほうが読ませる。**

2026-08-24、この節に「読ませる形にする」とだけ書いて「短く」を書かなかった結果、
**見出しが文になった。** 実測で最長30文字・平均19文字。**目次に9本並ぶと、読む前に疲れる。**

| ✕ 長い（30文字） | 「あと席の時間10分だからさっさと焼いちゃって」と言われました |
|---|---|
| ○ 短い（22文字） | 「あと席の時間10分だから…」と言われました |
| ✕ 長い（24文字） | いちばん確実なのは、店を出る前に次を取ることです |
| ○ 短い（18文字） | 確実なのは、店を出る前に次を取ること |

**引用を縮めるときは `…` を入れる。** 消して「あと席の時間10分だから」だけにすると、
**それが発言の全部に見える。** 全文は本文の引用ブロックに残す。

**数字は残す。**「900円」「23時」「100回」は目次で効く。**削るのは説明と語尾。**

**参考**: 分析担当が伸びている記事10本以上を実測したところ、**タイトル字数の中央値は18字**だった
（2026-08-24）。**見出しも同じ方向に寄せる。**

| ○ 読ませる見出し | ✕ 飾りの見出し |
|---|---|
| **900円のハラミが、特上よりうまかった** | 感想 |
| **予約は電話だけ。23時にかけるか、店で次を取る** | 予約について |
| **肉はうまい。ただ、接客には不満があります** | 気になった点 |

**⚠ この表の例は 2026-08-24 に差し替えた。**
**元は「特上を全部抜きました」「冷麺のことは、擁護できません」を良い例として載せていた。**
**どちらもオーナー指摘で直した表現である。** ルールの中に、直した表現が手本として残っていた。
→ **記事を直したら、ルールの例に同じ表現が使われていないか確認すること。**

### note誘導ポストは、記事の中心を出す（2026-08-24 オーナー指摘）

**2026-08-24 22:00、鶯谷園の記事へ誘導するポストを出して、オーナーが削除した。**

> **この焼肉屋、カードも電子マネーもQRも使えない**
> **1人6000円ほど、4人で2万4000円。全部現金で持っていく**

**オーナーの言葉**:
> **直近の焼肉note誘導ポストは酷すぎるので削除した。**
> **伝えたいことが現金しか使えないことになっていて、ひどい**

**記事の中心は「900円のハラミが特上よりうまかった」と「予約は23時にかける」。**
**現金のみは、本文4,200字のうち1段落しかない注意書き。**

#### なぜ起きたか

**記事を読み返して「ポストにしやすい断片」を探した。**
現金のみは**数字が入っていて短くまとまる**ので、材料として扱いやすい。
**扱いやすさで選んで、記事の中心を選んでいない。**

**送信前精査も止められなかった。** 分析担当は「会計で知って驚いた場面は材料に無い」と
**作り話の部分だけを指摘し、話題の選び方は見ていない。**
→ 担当は作り話を消して、**現金の話のまま**送った。

#### やること

| **タイトルと同じ話をする** | **記事のタイトルが、その記事の中心。** 誘導ポストはそこから外れない |
|---|---|
| **注意書きを見出しにしない** | 前提条件・制約・できないこと（現金のみ／予約制／時間制）は**開いた人が読めばよい** |
| **判定** | **「これを読んで開いた人が、記事の中身に納得するか」** |

**現金のみを先に出すと、記事が「支払いの注意喚起」に見える。**
**読み手が期待するものと、記事が渡すものがずれる。**

**この記事なら**: 「900円のハラミが、特上より速く無くなった」「電話は23時にかけると繋がる」。
**どちらもタイトルと本文の中心にある。**

#### 送信前精査に足す項目（分析担当へ）

**note誘導ポストは、事実の裏取りだけでなく、話題の選び方も見る。**

1. **記事のタイトルと、このポストは同じ話をしているか**
2. **その材料は、記事の中で何段落あるか**（1段落しかないものを中心に据えていないか）
3. **注意書き・制約を主役にしていないか**

### 見出しの本数は、話題の数で決まる（2026-08-24 オーナー指摘）

**話題が変わったら立てる。変わらないなら立てない。**

字数の目安（15〜25字）を守っても、**同じ話題で3本立てると目次が細切れになる。**
鶯谷園の記事は**予約の話が3本、接客の話が2本**あり、9本のうち5本が2つの話題だった。
→ **6本に整理した。**

#### 節をまとめたら、見出しもまとめ直す

**片方の話題しか指していない見出しを残すと、もう片方が目次から消える。**

| 実例 | 「席の時間」と「冷麺」を1つの節にまとめたのに、
見出しを **「90分制は納得。ただ、言い方がきつかった」** のままにした。
**冷麺の話が目次から見えなくなった**（オーナー指摘） |
|---|---|

→ **統合後の見出しは、統合したすべての話題を含む言い方にする。**
　 上の例は **「肉はうまい。ただ、接客には不満があります」** に直した。

#### 見出しは要約であって、本文の抜粋ではない

**本文の印象的な一文をそのまま持ってくると、読み手には文脈のない断片になる。**

| 実例 | **「「東京 焼肉」から自分で探しました」** は本文にそのまま出てくる文。

オーナー: **「読んでも読み手は？？となるはず」** |
|---|---|

→ **「この節には何が書いてあるか」を書く。** 本文から切り出さない。
　 上の例は **「鶯谷園はどんな店か。鶯谷駅から歩いて3分」** に直した。
| **私は、次の予約を取っていません** | おわりに |

**左側は、目次だけ読んでも記事の中身が分かる。** 右側は何も伝えていない。

**見出しだけを縦に読んで、記事の筋が通るか確かめること。** 通らなければ構成が悪い。

### オーナーの指摘を型で残す（2026-08-24 オーナー指示）

**`SNS運用/オーナー指摘.md`。書き手はメインセッションだけ。社員は起動時に読む。**

**オーナーが指摘するまで気づけなかったものは、検査が無いということ。**

### 文体カルテ（2026-08-23 追加・22:59 詳細化）

#### ① 行ごとの分解（いちばん重要）

### 口調カルテ（2026-08-24 オーナー指示・X向け）

**⭐⭐ 2026-09-17 追加（棚卸し・昇格8）— 属性が揃わないことを理由に、カードを作らないで終えない。**

| 3 | **ジャンル（暮らし・一人暮らし・自炊・家電・節約）と規模の近さは、絶対に外さない。**⛔ ここを外すと口調が別物になる |
| 4 | カードに**「属性不明 ◯人／確認済み ◯人」**を必ず書く。**⛔ 属性を推測して埋めない** |

**⛔ 「20代男性が見つからないので作れませんでした」は、今後は未実施として扱う。**

**桁違いの規模の人も見てよいが、「取れる／取れない」を分けて書く**（9章「大きいアカウントも見る」）。

| 一人称 | 自分／私／僕／俺／**なし**。**なしが何割か** |

|---|---|
| **借りない** | **体験。** その人が書いた出来事を、自分の話にしない |

### ファネルカルテ（2026-08-23 23:15 追加・毎日）

**このアカウントは有料noteを売るために存在している。入口だけ測って出口を測らない状態を終わらせる。**

いま測っているのは imp・リプ・いいね・スキ・フォロワー数で、**全部「入口の数」。**
どこで人が落ちているかが分からないと、「ポストが弱い」のか「プロフィールで止まっている」のか
「記事間の導線が無い」のか**永久に区別できない。**

#### 測る段

| 段 | 取得元 |
|---|---|
| Xのポストが見られた（imp） | ポストのアナリティクス |
| **プロフィールが見られた（プロフィールクリック）** | **ポストのアナリティクス。いままで一度も見ていない** |
| **bioのリンクが押された（リンククリック）** | **同上** |
| noteの記事が見られた（view） | note ダッシュボード |
| **無料記事から有料記事へ移動した** | note の流入元。**取れなければ「取れない」と書く** |
| 有料記事が見られた | note ダッシュボード |
| 買われた | note の売上 |

#### 出すもの（ファネル）

各段の**通過率**と、**いちばん落ちている段**を1つ名指しする。

| 通過率 | 計算 |
|---|---|
| imp → プロフィールクリック | クリック ÷ imp |
| プロフィール → リンククリック | リンククリック ÷ プロフィールクリック |
| note view → 有料記事 view | 有料view ÷ 全体view |
| 有料記事 view → 購入 | 購入 ÷ 有料view |

**「いちばん落ちている段」を毎日1つ名指しすること。** 全部を改善しようとすると何も動かない。

**取れない値は「取れない」と書く。推測で埋めない。**
X のアナリティクスは仕様変更で項目が消えることがある。消えていたらそう書く。

### 空回りさせない3つの規則

1. **明日試すことを1つだけ決める** — 複数決めると何も試さない。明日の投稿で検証できる粒度にする
2. **試した結果を翌日記録する** — impを見て効いたか書く。これがないと「分析した気になる」で終わる
3. **発見がない日は「なし」と書く** — 捻り出した観察は嘘になる
4. **1日1エントリ。窓ごとに増やさない。** 同じ日に複数の窓で観測したら、その日のエントリに追記する。
   「明日試すこと」は日をまたいで1つだけ。窓ごとに決め直すと何も検証できない

記録先は `SNS運用/ベンチマーク.md`。**X と note の両方で実施する。**
