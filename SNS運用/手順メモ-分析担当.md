# 手順メモ（分析担当）

**このファイルは 分析担当 だけが書きます。** 他の社員は読みません。**あなた専用のメモです。**

## 何のためのファイルか

**あなたは毎回まっさらな状態で起動します。** 昨日のあなたが苦労して解いた手順は、
記録しなければ消えます。**同じことを明日また一から解くことになります。**

実際に起きました（2026-08-24）。noteの一覧がページネーションだと分かるまで、
スクロールで何度も失敗しました。**次に同じ場所に来たとき、また同じ失敗をします。**

## 書くこと

**一度やって、うまくいったやり方。** 次に同じ場面が来たときに、そのまま使えるもの。

- **動いたコード・セレクタ・APIのエンドポイント**（そのまま貼れる形で）
- **失敗したやり方と、なぜ駄目だったか**（同じ穴に落ちないため）
- **何回目で成功したか**（回数が多いものは、ルールに昇格させる価値がある）

## 書かないこと

| その日限りのこと | 日報（`ログ/YYYY-MM-DD.md`）に書く |
|---|---|
| 判断基準・方針 | あなたが決めることではない。`改善提案.md` か日報で上げる |
| 長い説明 | **手順だけ。** 経緯は日報に書く |

## 書き方

新しいものを**上に積んでください。** 古いものほど下になります。

```
### （何をするときの手順か）— YYYY-MM-DD

**状況**: どういう場面で必要になるか（1行）
**やり方**: 手順。コードはそのまま貼れる形で
**やって駄目だったこと**: あれば
**所要**: 何回目で成功したか
```

## 大きくしすぎないこと

**このファイルは毎回あなたが読みます。** 長いと読む時間そのものが負担になります。

**200行を超えたら、古いものから削ってください。**
**繰り返し使っている手順は `運用ルール.md` に昇格させたほうがよい**ので、
その候補を `改善提案.md` に書いてください（昇格させるのはメインセッションです）。

### ⚠ 日別ファネルAPI — **返ってくる形は「入れ子」ではなく「平たい配列」** — 2026-08-25 訂正

**下の「X の日別 imp・プロフィール訪問」の項に `res.current_time_series と res.hourly_backfill を engagement_type で集計する` と書いたが、**
**`s.timeseries` や `s.data_points` を掘ろうとすると空になる。** 実際の要素は**これ1個で完結している**:

```
{count: 3, engagement_type: "ProfilePic", is_engaging_user_verified: "false", timestamp: 1787011200000}
```

**そのまま日付で足すだけでよい**（1回目で成功）:
```js
const agg={};
const add=a=>(a||[]).forEach(s=>{const k=new Date(s.timestamp).toISOString().slice(0,10);
  agg[k]=agg[k]||{};agg[k][s.engagement_type]=(agg[k][s.engagement_type]||0)+s.count;});
add(res.current_time_series);add(res.hourly_backfill);
```

**取れる engagement_type**: `Displayed`(imp) / `ProfilePic`(プロフィール訪問) / `Follow` / `Unfollow` /
`Fav` / `Reply` / `Detail` / `TweetCreate` / `ReplyCreate` / `HomeLinger` / `LingerTime`。
**フォロワー総数は `res.relationship_counts.followers`。認証済みは `res.verified_follower_count`。**

**⚠⚠ バケットは UTC 日。JST とは9時間ずれる。**
**「UTC の 8/25」＝ JST 8/25 09:00 〜 8/26 09:00。**
**夜の締め（JST 23:5x）に取ると、JST 0:00〜9:00 の9時間が前日のバケットに入ったままになる。**
**→ 日次の値として書くときは「UTC日バケット・取得時刻つき」と必ず添える。**

**⚠⚠⚠ imp は何日も増え続ける。同じ日の値でも、いつ測ったかで倍違う。**

| 8/24 の Displayed | **385**（8/25 00:1x 取得）→ **428**（8/25 12:2x）→ **855**（8/25 23:4x） |
|---|---|

**→ 日をまたいだ比較は「同じ経過時間で測った値どうし」でしかできない。**
**台帳に書くときは必ず取得時刻を併記する。** 8/25 の 365 と 8/24 の 385 は**同じ齢**なので比較してよい。

### ⚠ 起動プロンプトの「現在時刻」を信じない。必ず `date` を打つ — 2026-08-25

**状況**: 毎回いちばん最初。**これを飛ばすと、全部の判断がずれる。**

**その後20分ぶんのツール呼び出しの間に「もう00:04を過ぎた」と思い込み、note の数字を早く取りかけた。**
**→ `date` は10ツール呼び出しごとに打ち直す。** 日付をまたぐ判断の直前は必ず。

**あわせて見るもの**（同じ呼び出しでまとめて取る）:
```bash
ls -la "/Users/kyoichi/Claud用/SNS運用/ログ/"
```

→ **mtime が止まっていたら「作業していない」ではなく「待っているかもしれない」と読む。**

### 数字を読むときに、繰り返し間違えたこと — 2026-08-24／**8/25 追記**

**imp を比較するときは経過時間を揃える。** 揃えないと、同じポストが伸びていく曲線を、
別々のポストの優劣として読んでしまう。**2回誤警報を出した。**

**母数が小さい段を「落ちている」と書かない。** プロフィール訪問 0/49 は、
通過率2%でも期待値1件なので**ブレの範囲**。「壊れている」と書けるだけの母数があるか先に確認する。

**n が小さければ「差なし」と書く。** n=4 はコイン投げと区別がつかない。

**⭐ 8/25 追記: 3時間後imp では型を弁別できない。**
**同じ日の4本が、型が違うのに 23:04 時点で全部 21〜23 に収束した。**
**13:11 のポストは 3時間後 5 → 9時間53分後 23。** 3時間後の値は「どれだけ早いか」しか見ていない。
→ **施策の判定に3時間後impを使わない。** 詳細は `施策台帳.md` の施策1の判定。
