# 競馬予想AI（回収率狙い・投資型） — 検証MVP 設計書

- 日付: 2026-07-05
- ステータス: 承認済み（実装計画の作成へ）
- スコープ: **Phase 1（データ収集）＋ Phase 2（MLモデル＋回収率backtest）** のみ
- スコープ外（別スペック）: Phase 3（次走予測＋予想家ブレンド）、Phase 4（Web化）

---

## 1. 目的とゴール

AIで JRA 中央競馬の**回収率狙い（期待値プラス馬券を機械的に探す投資型）**の予想を行う。
本スペックのゴールは UI ではなく、**次の問いに答えること**：

> 過去データで「期待値プラスの馬券だけを買い続けたら、回収率は 100% を超えるか？」

これは本プロジェクト全体の **GO / NO-GO 分岐点**。ここを突破できなければ後続フェーズ（次走予測・予想家ブレンド・Web化）に進む意味がないため、最優先で検証する。

### 成功基準
- 過去5年ぶんの JRA 中央全レースをローカル DB に収集できている。
- 時系列分割の backtest で、単勝・ワイドそれぞれの「期待値プラス馬券」戦略の回収率が数値で出力される。
- 回収率レポート（券種別・期待値しきい値別・オッズ帯別）が再現可能な形で生成される。
- 判断材料として、モデルの**キャリブレーション**（予測勝率と実際の勝率の一致度）が確認できる。

### 非ゴール（YAGNI）
- 予想家（X/YouTube）の意見の取り込み → Phase 3。
- Web UI・リアルタイム予測 → Phase 3/4。
- 三連単・三連複など組合せ爆発する券種 → 対象外（単勝・ワイドのみ）。
- 地方競馬 → 対象外（JRA 中央のみ）。

## 2. 全体アーキテクチャ

```
[netkeiba]
   │  スクレイピング（間隔を空ける／ローカルキャッシュ／中断・再開可）
   ▼
[生HTMLキャッシュ] ──parse──▶ [SQLite: race.db]
                                   │
                                   ▼
                            [特徴量生成]
                                   │
                                   ▼
              [LightGBM 学習: 1着確率モデル / 3着内確率モデル]
                                   │
                                   ▼
        [時系列 backtest: 期待値計算 → 回収率レポート]
```

パーツは独立した Python モジュールに分け、各段の出力（HTMLキャッシュ・DB・特徴量テーブル・モデルファイル・レポート）をファイルとして残す。各段は単独で再実行・テスト可能にする。

### 技術スタック
- 言語: Python（既存アプリと同系統）
- 収集: `requests` + `BeautifulSoup`（+ 必要に応じ `lxml`）
- 保存: SQLite（`race.db`）
- 特徴量/分析: `pandas`
- モデル: `LightGBM`
- backtest/レポート: Python スクリプト → CSV / 標準出力の表
- 出力形式: 本 MVP は**コマンド実行＋CSV/表**（Web 化は Phase 4）

### ディレクトリ構成（案）
```
競馬予想AI/
  scraper/        # 収集・パース
  db/             # スキーマ・DBアクセス
  features/       # 特徴量生成
  model/          # 学習・推論
  backtest/       # 期待値計算・回収率レポート
  data/
    cache/        # 生HTMLキャッシュ
    race.db
  tests/
  requirements.txt
```

## 3. Phase 1: データ収集

### 3.1 収集対象
- JRA 中央競馬、直近5年（2021-01 〜 2025-12 目安。実装時に確定）。
- 各レースについて: 出馬表、確定着順、単勝オッズ、払戻（単勝・ワイド）。

### 3.2 netkeiba への配慮（必須要件）
- **1リクエストごとに数秒スリープ**（例: 2〜4秒、ジッター付き）。
- **取得済みページはローカルにキャッシュ**（`data/cache/`）し、**再取得しない**。
- **中断・再開できる**設計（どこまで取得したかを記録し、途中から再開）。
- User-Agent を明示。エラー/レート制限時はバックオフ。
- 収集は数回に分けて回せる前提（5年ぶんは数万レース）。
- 個人の学習・検証目的での利用。取得データはローカル保持のみ。

### 3.3 DB スキーマ（SQLite）
- `races`: race_id(PK), date, course（開催場）, distance, surface（芝/ダート）, going（馬場状態）, class, num_runners, weather 等
- `entries`: id(PK), race_id(FK), horse_id, jockey, trainer, draw（枠番）, horse_no（馬番）, weight_carried（斤量）, win_odds（単勝オッズ）, **finish_pos（着順＝正解ラベル）**, time, last_3f（上がり3F）, margin（着差）
- `horses`: horse_id(PK), name, sex, age（レース時点の性齢は entries 側でも保持可）
- `payouts`: race_id(FK), bet_type（win/wide）, combination, payout（100円あたり払戻）, popularity

インデックス: `races.date`, `entries.race_id`, `entries.horse_id`。

### 3.4 パース方針
- ページ種別ごとにパーサ関数を分離（レース結果ページ / 馬ページ 等）。
- HTML 構造変化に備え、パーサは**キャッシュ済みHTMLに対して単体テスト**できるようにする（代表HTMLを tests に固定）。

## 4. Phase 2: モデル ＋ 回収率検証

### 4.1 特徴量（入力）
まず素直に効くものから。**オッズ（人気）は特徴量に入れない**（市場追従を防ぎ期待値プラス馬券を見つけるため。オッズは §4.4 の期待値計算でのみ使用）。

- 馬: 近走の着順・着差・上がり3F、休養明けか（前走からの間隔）、距離/馬場実績、斤量
- 枠・属性: 枠番、性齢
- 人: 騎手・調教師の直近勝率／複勝率（**データリーク防止のため当該レース時点までの実績のみで算出**）
- レース条件: 距離、馬場（芝/ダート）、馬場状態、クラス、頭数

**データリーク厳禁**: すべての集計系特徴量は「そのレースの発走時点で知り得る情報」のみで作る（未来の着順・オッズを混ぜない）。

### 4.2 モデル
- LightGBM を2つ学習:
  - **モデルA: 1着確率**（単勝用）
  - **モデルB: 3着内確率（複勝圏内）**（ワイド用）
- 学習後、**レース内で確率を正規化**（同一レースの1着確率の合計＝1 になるよう調整）。

### 4.3 ワイドの2頭同時確率
- 各馬の3着内確率から **Harville 型の近似式**でペアの同時「両方3着以内」確率を算出。
- まずは近似でよい。精度は backtest とキャリブレーションで確認し、不足なら改善（順位分布モデル等）を後続で検討。

### 4.4 期待値と馬券選定
- 単勝の期待値: `EV = 予測勝率 × 単勝オッズ`（100円基準なら `勝率 × オッズ × 100 − 100`）。
- ワイドの期待値: `EV = ペア的中確率 × ワイド払戻見込み`。
  - ワイドは確定オッズが事前に一意でないため、**backtest では実績払戻（payouts）を用いて答え合わせ**する。運用時（Phase 3）の見込みオッズ扱いは別途設計。
- **買い目条件**: `EV > しきい値`（例: EV > 1.0 = 期待値プラス。しきい値は複数試す）。

### 4.5 backtest（回収率検証） — 最重要
- **時系列分割**で学習/検証を分ける（例: 過去→未来へローリング。未来データで学習しない）。
- 検証期間の各レースで、学習済みモデルから買い目を選定 → **実際の払戻で回収率を計算**。
- 回収率 = 総払戻 / 総投資。券種別（単勝 / ワイド）に算出。
- **レポート出力**（CSV＋表）:
  - 券種別回収率、的中率、購入点数、収支
  - 期待値しきい値別（EV>1.0 / 1.1 / 1.2 …）の回収率
  - オッズ帯別の回収率
  - モデルの**キャリブレーション曲線**（予測勝率 vs 実勝率）
- **GO/NO-GO 判断**: いずれかの設定で回収率が安定して 100% を超えるか。超えなければ、特徴量・モデル・戦略の改善余地を検討（それでも超えなければプロジェクト方針を再検討）。

## 5. テスト方針

- **パーサ**: 固定した代表HTML（キャッシュ）に対する単体テストで、期待するフィールドが抽出できることを検証。
- **特徴量**: データリークが無いことのテスト（未来情報が混ざらない）。小さな合成データで集計ロジックを検証。
- **期待値/回収率計算**: 既知の入力（勝率・オッズ・払戻）に対し EV と回収率が手計算と一致することを検証。
- **backtest 分割**: 学習期間と検証期間が時系列で重ならないことのテスト。
- TDD（test-first）で各モジュールを実装。

## 6. リスクと対策

| リスク | 対策 |
|---|---|
| netkeiba の HTML 変更でパース破綻 | パーサをキャッシュHTMLに対してテスト化。パーサ層を薄く分離 |
| スクレイピングのブロック/負荷 | スリープ＋ジッター、キャッシュ再利用、中断再開、バックオフ |
| データリークで回収率が過大評価 | 全特徴量を発走時点情報に限定、時系列分割、リーク検知テスト |
| 市場が効率的で回収率が100%を超えない | これは検証の結論そのもの。しきい値/オッズ帯を層別に分析し、勝てる部分市場があるか探る |
| ワイド同時確率の近似誤差 | キャリブレーションで確認、不足なら順位分布モデルへ |
| 5年ぶん収集の時間コスト | 中断再開＋数回に分割。まず少量で全パイプラインを通してから全量収集 |

## 7. 段階的な進め方（実装順の指針）

1. DB スキーマ＋パーサを**少数レース**で通す（スクレイピング→DB）。
2. 特徴量生成を少量データで作り、リーク検知テストを通す。
3. LightGBM 学習→小規模 backtest でパイプライン全体を疎通。
4. 5年ぶんを本収集（中断再開で数回に分割）。
5. 全量で学習→backtest→回収率レポート→**GO/NO-GO 判断**。

## 8. 継続学習ループ（Phase 5・実運用で成長させる）

要件: **予想後に結果を参照して、どんどん学習・成長する。** 方式は「定期再学習＋成績記録」の両輪（リアルタイム更新は非採用）。

- **定期再学習**: レース確定後に結果を自動で収集し DB に追加 → 毎週/毎月など定期でモデルを作り直す。新しい傾向（馬場・血統・騎手の調子）を取り込み、自動で強くなる。
- **成績記録（成績台帳）**: 各予想を「予測時点の勝率・期待値・買い目・使用モデルのバージョン」とともに記録し、確定後に実払戻で答え合わせ。**回収率・的中率の推移**を残し、人間が監視・微調整できるようにする。
- 判断材料: モデルのバージョン別・期間別の回収率推移。悪化したら再学習や特徴量・戦略の見直しを行う。

### 本 MVP がこの成長を阻害しないための前提（MVP スコープ内で守る）
- DB は**日付ベースで追記できる**設計にする（新しいレースを足しても既存を壊さない）。
- 学習・backtest は**時系列で再実行可能**にする（データが増えたら作り直せる）。
- モデル出力に**バージョン/学習期間を紐付け**られるようにしておく（成績台帳の布石。MVP では最低限モデルファイルにメタ情報を残す）。
