# SNS分析担当 設計書

2026-08-23 / オーナー: 竹田喬一

## なぜ作るか

SNS担当は窓ごとに6工程を回している。うち3つが分析（観測・ポスト前のimp確認・トレンド調査）で、
**締切のある作業に押し出されて、測定系が真っ先に落ちる。**

2026-08-23の実測:

| 窓 | 落ちた作業 |
|---|---|
| 21:00 | Xいいね0件・noteスキ0件・note返りの確定・棚卸しは54/200で中断 |
| 22:00 | Xいいね0件・こちらからのリプ0件・棚卸し未着手 |

一方、**リプ返信は一度も落ちていない。** 窓は締切のあるものを守り、測定を捨てる。
これは配分の失敗ではなく、**窓という単位に測定を載せていることの構造的な帰結。**

→ **測定と分析を窓の外に出す。**

## スコープ

### やること

1. 数値集計と停止条件の判定
2. 伸びている人の観測と「今日試す型」の決定
3. ネタ候補の用意（時事・トレンド・在庫）
4. 前日ログの読み返しと、発見のルール化提案
5. 窓の欠測検知
6. note原稿の精査（投稿前レビュー）

### やらないこと

- **X・note への書き込みを一切しない。** 読み取り専用
- **運用ルール.md を書き換えない。** 提案までにとどめる
- **note原稿を編集しない。** 指摘と可否判定まで
- ポスト・リプ・いいね・スキ・フォローの実行（すべてSNS担当の仕事）

## 役割とファイルの所有権

2つのエージェントは別セッションで動くため、**直接会話できない。受け渡しはファイル経由**になる。
上書き合戦を構造的に防ぐため、**1ファイル1書き手**を原則とする。

| ファイル | 書く人 | 読む人 |
|---|---|---|
| `SNS運用/分析ブリーフ.md`（新規） | 分析担当（毎回上書き） | SNS担当 |
| `SNS運用/数値台帳.md`（新規） | 分析担当（追記） | オーナー |
| `SNS運用/改善提案.md`（新規） | 分析担当（追記） | メインセッション |
| `SNS運用/note精査結果.md`（新規） | 分析担当（追記） | メインセッション |
| `SNS運用/ベンチマーク.md` | 分析担当（SNS担当から移管） | オーナー |
| `SNS運用/ログ/YYYY-MM-DD.md` | SNS担当 | 分析担当（読むだけ） |
| `SNS運用/引き継ぎノート.md` | SNS担当 | 分析担当（読むだけ） |
| `SNS運用/運用ルール.md` | メインセッション | 両方（読むだけ） |

**どのファイルにも書き手が1人しかいない。**

## 稼働タイミング

| 回 | 時刻 | 目的 |
|---|---|---|
| 朝 | **6:30** | 前日の結果を集計し、その日一日ぶんのブリーフを作る。7:00の窓から使える |
| 夕 | **16:30** | 午前の結果を見て、後半のネタと数字を差し替える。17:00の窓から使える |

**窓とぶつからない時刻を選んでいる。** 窓は毎時0分（+17秒）に始まり、実測で約18分かかる。
6:00に窓はないので6:30は安全。16:30は16:00の窓（16:00〜16:20頃）が終わったあとで、
17:00の窓が始まる前。**どちらもChromeを取り合わない。**

分析担当が遅れて16:50を過ぎた場合は、**その回を打ち切ってブリーフを更新せずに終える。**
古いブリーフが残るほうが、窓と衝突するより安全（SNS担当は発行時刻で鮮度を判断できる）。

note精査だけは定時ではなく、**原稿が所定の場所に置かれたときに実行**する（メインセッションから依頼）。

## 分析ブリーフの仕様

`SNS運用/分析ブリーフ.md`。**毎回まるごと上書きする。** 追記すると読む量が増えて読まれなくなる。

先頭に必ず発行時刻を書く。

```
発行: 2026-08-23 06:30
```

載せる項目は**4つだけ**。

| 項目 | 中身 |
|---|---|
| 今日試す型 | **1つだけ。** 実例（誰のどの投稿か）と、なぜ効いたかの仮説を添える |
| ネタ候補 | 3〜5件。時事・トレンド・自分の在庫から。**それぞれ「なぜ今日か」を1行** |
| 直近の数字 | 直近5本のimp、note返り（スキあたりのview）、停止条件の判定結果 |
| やらないこと | 今日は触るなという話題。理由を1行 |

### 鮮度の扱い

SNS担当は、ブリーフの発行時刻を見て次のとおり扱う。

| 経過 | 扱い |
|---|---|
| 8時間以内 | 全項目そのまま使う |
| **8時間超** | **ネタ候補は使わない。** 型と数字だけ使い、ネタはその場で考える |

理由: 6:30発行のブリーフを22:00の窓が時事ネタとして使うと外す。数字と型は劣化が遅いが、
時事は速い。**同じファイルの中で項目ごとに寿命が違う。**

## 停止条件の判定を移す

現状はSNS担当が窓ごとに自分で判定しているが、**時間切れの窓では最初に落ちる。**
分析担当が1日2回きちんと計算し、ブリーフに次のいずれかを書く。

- `通常運転`
- `要注意`（理由を明記）
- `停止`（該当した条件を明記）

SNS担当は**読むだけ**。自分で計算しない。ただし窓の中で明らかな異常（弾かれ・警告表示）に
気づいた場合は、その場で止まる判断を従来どおり行う。

## note原稿の精査

### 流れ

1. メインセッションが原稿を `SNS運用/note下書き/` に置く
2. メインセッションが分析担当を起動し、対象ファイル名を渡す
3. 分析担当が精査し、`SNS運用/note精査結果.md` に追記する
4. **可否を判定する**（`このまま出せる` / `直してから出す`）
5. `直してから出す` の場合、メインセッションが修正して再精査にかける
6. `このまま出せる` になってから投稿する

**分析担当は原稿を編集しない。** 書き手と査読者を分けるのが精査の目的であり、
査読者が直すとその修正を誰も見ないことになる。

### 精査で見る項目

| 観点 | 内容 |
|---|---|
| 文体 | `運用ルール.md` 1章の禁止語（効く／仕組み／構造／結果的に／〜な気がします 等）の残存 |
| 意味づけ | 体験を教訓に翻訳していないか。最後の一文が説教になっていないか |
| 事実 | 数字・固有名詞・製品名の誤り。裏が取れない断定 |
| 利益相反 | **クレジットカードの紹介・アフィリエイトが混入していないか**（本業がカード会社のため禁止） |
| 著作権 | インターネットから拾った画像の使用がないか |
| 有料ライン | 有料記事の場合、無料部分だけで価値が完結していないか／有料部分に中身があるか |
| 導線 | 他記事・Xへの導線が機能しているか。タグが10個埋まっているか |

## 改善提案と欠測検知

### 発見のルール化

SNS担当が窓の中で見つけた解法は、**その窓のログには残るがルールには載らない。**
次の窓は前提から解き直す。

実例（2026-08-23）: 22:00窓がnoteの一覧をAPI取得で解決した。同じログに「Xはスクロールで詰まる」も
書いてあったが、繋がらなかった。**同じファイルに答えと問題が並んでいたのに転用されなかった。**

→ 分析担当は朝の回で**前日のログを通しで読み返し**、次を `SNS運用/改善提案.md` に書く。

- この窓の発見は、別の場所でも使えないか
- 同じ失敗が複数の窓で起きていないか
- ルールに書いていないのに毎回やっていることはないか

**ルール本体は書き換えない。** 提案を読んでメインセッションが反映する。
分析担当がルールを書けると、SNS担当の行動が誰の承認もなく変わる。

### 欠測検知

朝の回で、前日に**動くはずだった17回（7:00〜23:00）のうち何回動いたか**を数え、
欠測があれば `改善提案.md` の先頭に書く。

判定材料は**ログ内の窓ごとの見出し**とする。プロセスの生存やタスクの `lastRunAt` は
「起動した」ことしか示さず、**実際に作業したかを示さない。**

実例（2026-08-23）: 8/22が丸一日欠測し、21:00がスキップされた。どちらも
**オーナーの指摘で初めて発覚した。** 誰も数えていないと欠測は気づかれない。

## 安全設計

| 項目 | 内容 |
|---|---|
| 書き込み | **X・note へ一切書き込まない。** 読み取り専用 |
| 合言葉 | 起動プロンプトに `起動元=sns-analyst-window` を要求する。無ければファイル書き込みもしない |
| 停止条件 | 分析担当自身には不要（書き込まないため） |
| 二重稼働 | 書き込み先が `分析ブリーフ.md`（上書き）のみなので実害が小さい。ただし発行時刻で検知はする |

**読み取り専用という制約が、そのまま安全性の証明になる。** SNS担当に必要だった防御の大半が要らない。

## 数値台帳の粒度

**まず日次で始める。** 1日1行に、その日の合計（imp・リプ・いいね・スキ・フォロー増減・
noteのview/スキ）を記録する。窓ごとの粒度は、日次で説明できない変動が出てから足す。

先に細かくすると、**埋めることが目的になって読まれなくなる。**

## 残っているリスク

**Chromeのタブを分析担当とSNS担当で共有する。** 時刻をずらして衝突は避けたが、
窓が長引いた場合や手動起動が重なった場合は同時に触りうる。

対策として、分析担当は**タブを自分で作り、終わったら必ず閉じる**。
（2026-08-23に実測: タブ0枚から `tabs_context_mcp` の `createIfEmpty: true` で作り直せる。
ログインはCookieに残るので消えない）
